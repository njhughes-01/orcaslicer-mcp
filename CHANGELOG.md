## [Unreleased]

### Added
- Direct CC2 CANVAS auto-refill switch: `cc2_set_auto_refill` (method 2004) turns the printer's auto-refill switch on or off with one boolean, and it is shipped as the labelled candidate it is: **no CC2 has ever answered 2004 on this project, so every reply carries `verified_on_this_printer: false` beside a sentence naming why**, and the one thing that can move that label is a real print, which has not happened. What is established is first-party and narrow, and it is all this tool uses: Elegoo's own LAN web client, the bundle the printer serves itself, defines `SetAutoFillFilament = 2004` and `GetCanvasInfo = 2005` in its own method enum, sends `{method: 2004, params: {auto_refill: <the toggle's boolean>}}`, treats a nonzero `error_code` as the failure it shows as "Failed to set auto refill.", and paints the very same toggle from `canvas_info.auto_refill` of the 2005 reply — one field name on the way in and on the way out, which is why that field is the only thing this command ever carries. **The trap in this family is the older integration protocol manual, which spells the parameter `enable`,** both in its methods table and in its own worked example, while its own 2005 sample answers `auto_refill` and the integration that ships that manual defines the 2004 constant and never sends it. Unlike the light (1029), where the two documented spellings are paired in one command because both are attested, `enable` is never sent here in any combination: pairing an undocumented field because one table names it is how a printer gets told something no client of Elegoo's ever has, and that same manual's table makes the identical class of mistake on the delete command (`filename` where Elegoo's own client sends `file_path`), so a table row of that manual is not proof about this firmware. Because 2004 lives beside 2003 (which writes a tray's filament info) and the 2005 reply carries `active_canvas_id` and `active_tray_id` next to the flag, one field is also a safety property: a call here cannot move which tray the printer prints from, rename a spool or touch a slot map, and tests pin on the recorded wire that no other method — 2003, 2005 as a command, or any file, job or heater method — ever accompanies it. It is two-phase exactly like every other control here: without `confirm=true` a call sends only the read-only 2005 and previews what the printer says now and the exact one-field command a confirmed call would send; only an exact `confirm=true` sends it, once, waited for 10 s (Elegoo's client passes no override for this method, so that client's 5 s default applies, and the integration waits 10 s for every command — the longer is taken, and nothing is ever resent to catch a slow answer). Accepted (an explicit `error_code` 0 — the printer not refusing), refused (its code kept, and it earns no further read) and ambiguous (no answer, an unreadable one, or a dropped session) are kept apart with the job controls' own vocabulary, imported rather than reworded. The read-back deliberately does **not** reuse `cc2_state`'s canvas reader: a status line has to answer, so that reader defaults an absent `auto_refill` to false, and for a control's read-back an absent field is not a reading — so an absent field, a 2005 that was refused or never answered, and a value that cannot be read each stay unknown with whatever did arrive kept beside them, while the integers 0 and 1 read as the numbers they are (the integration's own CANVAS model records another Elegoo machine answering int 1 where its client expects a boolean). One deliberate difference from the light and the speed mode: a CANVAS read that answers nothing does not block the preview or the change, because a printer with no CANVAS attached is a legal state for a switch the printer stores for itself, and refusing a preview for that reason would be a barrier the plan forbids; it is reported as unknown with its reason instead. After an accepted or unanswered command exactly one read-only 2005 reports the flag as a fact of its own, and a look that contradicts the command the printer just accepted is said out loud without ever earning a second command. Covered by `tests/test_cc2_canvas.py` and the auto-refill section of `tests/test_server_cc2.py` (the parameter bar, the one-field wire shape, `enable` proven never to leave, the unknown-preserving read-back, accepted/refused/ambiguous, exactly-once on the recorded wire including a lost answer and a dead session, the note-length caps, both phases at the tool layer, and the tool in the default-posture and fresh-interpreter discovery probes). No printer, Home Assistant, Mac, network or credential was touched, and nothing was committed, pushed or deployed: every test is a scripted reply, and the live test (idle printer, a CANVAS with a spare tray, Nathan's yes for the switch, a print run to one empty tray, the setting restored) is recorded as open in `openspec/changes/cc2-direct-print/revised-plan.md`.
- Direct CC2 print history: `cc2_print_history` (method 1036) reads the prints the printer lists for itself, and it is the first read on this server whose **reply shape has never been captured from a real CC2**, so it is shipped labelled as the candidate it is rather than as a verified feature. What is established is first-party and narrow: Elegoo's own LAN web client — the one the printer serves — asks `{method: 1036}` with **no parameters at all**, waits 30 s for it at that one call site, treats a nonzero `error_code` as "Failed to get print history", and reads `history_task_list`, whose entries it reads as `task_id`, `task_name`, `begin_time`, `end_time`, `task_status` and the four `time_lapse_video_*` fields; its duration column subtracts `end_time` from `begin_time`, which is that client's own proof that both stamps are unix seconds, and its status column is painted from the app's own table (`0 other, 1 complete, 2 cancel, 3 cancel, 4 printing, 5 pause`, anything else "Unknow"). Every one of those is used as the client's, and labelled as such — the status number is always carried next to the app's word for it, because that table is an app's vocabulary rather than a protocol's and two of its numbers share a word, and no unit or meaning at all is claimed for the time-lapse numbers. What is *not* established is everything else, so the tool refuses instead of guessing: a reply with no `history_task_list`, a list that is not a list, and an entry that is not an object each refuse with their own reason, naming key names but never values, one request, nothing fitted afterwards — and **no reply is claimed to have been tested on hardware: every test is a scripted reply, and each successful reply carries `verified_on_this_printer: false` beside a sentence saying why.** Two traps are pinned by tests. The community protocol manual lists 1036 with `{"page": 1, "page_size": 10}`, and that row matches Elegoo's *cloud* ("RTM") history call — which paginates with `pageNumber`/`pageSize` and answers camelCase `taskList`/`totalTasks`, with its four time-lapse fields hard-filled to zero — so no paging key of any kind is ever sent here, none of the camelCase names is ever read, a cloud-shaped reply refuses with a reason of its own, and a `totalTasks` sitting beside a LAN list is never borrowed as the count that makes the list look self-accounting. And because the request carries no page size, the printer decides how long the answer is: the reply caps itself at 100 entries and then says so loudly (`truncated_in_reply`, both counts, a warning naming that it is not the whole history and that there is no next page to ask for, because 1038 removes history entries and this server does not send it), with the cap deliberately set under this server's own 200-per-list sanitiser cap so a truncation is always this tool's honest sentence and never a silently dropped row. `complete: true` is earned only when the printer's own `total` meets the entries it actually sent and nothing had to be dropped; a total above them, below them, unreadable or absent each get their own sentence, an unreadable total keeps the entries it could read rather than destroying them, and an empty list with no count says the only true thing available — that an empty history cannot be told apart from a firmware that keeps history somewhere else. Missing fields stay null *and* named in that entry's `not_reported`; `0` stays "not recorded" rather than becoming midnight 1970 or a zero-length print; a reversed pair of stamps earns no duration; and a stamp too large for seconds is reported as suspiciously milliseconds-shaped and left unconverted. Text over 255 characters is **withheld with its length named, never cut** — this server's own sanitiser caps strings at exactly that length, and a plausible-looking half name would be worse than no name, so the bound has to withhold before the reply is made safe (a 900-character name is proven never to reach the reply, not even its tail). Entries stay in the printer's own order, unsorted and un-de-duplicated, because the official app sorting them for its own table is that app's business. The one field that can carry a credential is handled: a time-lapse link with a login in its authority is withheld and only its presence reported, the same rule the transport applies to a printer address carrying a login. **1037 (one print's detail) and 1038 (deleting history) are omitted, not implemented and not advertised**: `GetHistoryTaskDetail` appears in Elegoo's entire 3.6 MB web bundle exactly twice, both in the enum that defines it, never called, so it has no published request, response or caller, and this server will not take a `uuid` from a live 1002 status frame and send it somewhere as a task handle. Covered by `tests/test_cc2_history.py` (82 tests) and the history section of `tests/test_server_cc2.py` (10 tests, including the parameterless wire shape, the candidate label, all four unreadable-reply shapes, the truncation, the withheld login-bearing link and the sanitiser-ceiling proof), plus the tool in the default-posture and fresh-interpreter discovery probes. No printer, Home Assistant, network or credential was touched, and nothing was committed, deployed or run against a machine.

### Changed
- The direct CC2 tools no longer hide behind `ORCA_CC2_READ` and `ORCA_CC2_WRITE`, and both variables are gone. Configuring the printer is the only opt-in there is: `cc2_status`, `cc2_list_files`, `cc2_upload_gcode`, `cc2_start_print`, `cc2_pause_print`, `cc2_resume_print` and `cc2_stop_print` are listed by any server, exactly like every other tool, whether or not a printer is configured. What changed is discovery, not reach: with no `ORCA_CC2_URL` set, every one of these tools still refuses, honestly and in this process, with `not_configured` and `printer_contacted: false`, before any name is looked up and before any socket is opened, and an address that carries a login or points somewhere public is refused the same way without echoing it. `ORCA_CC2_URL` and the access-code variables keep working as before, and so does every non-CC2 tool.

### Added
- Direct CC2 temperature control: `cc2_set_temperature` (method 1028) sets **one** heater's target — `extruder` (the nozzle, also read as `nozzle`) or `heater_bed` (also `bed`), one heater per command, the two frames Elegoo's own LAN control sends — and it is two-phase like every other control here: without `confirm=true` a call only reads the printer and previews the exact one-heater command and the ceiling it enforced, and no command leaves the wire. The point of this entry is where the numbers come from, because a heater tool that guesses is a hazard: **the ceiling is the input bounds of Elegoo's own official LAN control for this printer — 0-350 for the nozzle and 0-110 for the heated bed** (its web client, release 20260625, whose input handler clamps a typed number into them before it sends), and every reply carries the bound with that source named beside it and the words "not a hardware rating", because that is exactly what it is. Nothing else in the sources was usable as a limit and none of it was quietly adopted: the firmware's own `max_temp` from Elegoo's published CC2 config (600 extruder, 125 bed) is a sensor envelope that Elegoo's `heaters.cpp` refuses outside, which is a safety window rather than a target; the same Elegoo SDK's capability row records 300 for that extruder and 120 for that bed while binding those five values against a struct whose field order turns them into "minimum 300, maximum 1", so the row contradicts itself; and the official Elegoo profile bundle for this machine carries **no temperature-ceiling key of any kind**, which is the plainest possible reason why a slicer profile's nozzle or bed number is a print setting and can never be read as a machine limit for other filaments or nozzles. So the tool refuses above its sourced ceiling and **offers no parameter to raise it** — a caller-supplied "verified limit" argument would be the guess dressed up as an input — while any lower number is always open. A nozzle setpoint above the 300 the other Elegoo source names is sent, because the machine's own control reaches that high, with a note saying the two sources disagree and nothing claiming the printer is rated for it. `'chamber'` refuses before a session opens (its official control row is not editable and the published firmware config gives the box a sensor with no heater), as does anything that is not one of the two heaters, a setpoint that is not a number, or a number outside 0 to that heater's own ceiling — 320 is legal for the nozzle and illegal for the bed, because the ceilings are per heater and no single number was assumed. `0` is legal and is labelled for what it is: a heater turning off, the same thing this printer's own end-of-print G-code sends. One 1028 command per call, sent once and never resent, waited for 10 s (the longer of the LAN client's 5 s default for this method and the integration's 10 s for every command); accepted / refused / ambiguous are kept apart exactly as the job and peripheral controls keep them, a lost answer is never a refusal and never earns a resend, and after an accepted or unanswered command exactly one read-only look reports both the target and the actual temperature the printer states, kept apart from acceptance: a target still climbing is never read as a failure, an absent field stays unknown rather than becoming zero, and a target stated as anything other than the number just accepted (past a stated half-degree) is said out loud without earning a second command. Found in Elegoo's own sources, and pinned by `tests/test_cc2_temperature.py` and the temperature section of `tests/test_server_cc2.py` (mocked only: no printer was contacted, and the ceiling is a documented bound, not something probed by sending an out-of-range value, which the plan forbids).
- Direct CC2 information reads: `cc2_printer_info`, `cc2_file_detail` and `cc2_file_thumbnail`. All three are reads, each one request asked exactly once, and they fill the three questions the status frame cannot answer. `cc2_printer_info` (method 1001, no parameters) is what the printer says it is — model, its own name, serial, firmware/hardware/protocol versions, build volume and resolution, network type, remaining memory, camera and USB attachment — and it is the only place this server reads a firmware version from. `cc2_file_detail` (1046) is one file on the printer: size, total layers, the slicer's estimated time and filament, when it was created, how often and when last it printed, and its colours per tool, in the same words `cc2_list_files` already uses for those same facts. `cc2_file_thumbnail` (1045) returns the printer's own embedded preview for a file as an MCP image with one line of text beside it. None of the three invents a field: everything the printer did not answer is null and named again in `not_reported` (this firmware is measured answering two of its three version strings empty, and an empty string is not a version), the attributes reply carries the printer's `ip` and `mac` nowhere, and it says so plainly when the serial in the reply is not the serial the session pinned. Three ways a reply can be unhelpful are said instead of smoothed: a layer count that arrives under two field names with two different numbers is reported as both with the name that was used, a detail reply about a different file than the one asked for is reported as that, and a printer that answers none of a method's documented fields is refused rather than reported as an empty profile. Two wire facts are pinned by tests because they are the trap of this family: 1046 is sent `filename` and 1045 is sent `file_name`, so the two file reads are not interchangeable, and only `local` storage is ever asked for — the removable volumes are spelled two different ways by the two first-party sources and have never been offered to this firmware, so those spellings refuse instead of being guessed. A file name is held to the bar `cc2_list_files` prints by (no path, no control characters, at most 255 characters) and refuses before a session is opened, so these tools cannot be used to poke above the printer's own file store. The thumbnail is decoded, typed by its bytes' own signature rather than by the manual's \"typically PNG\", and bounded: an image over 2 MiB is refused with its size named and never truncated, because a half an image is a corrupt image and the image rides inside one tool reply. The fan (1030), the print history (1036/1037), the camera (1042) and file deletion (1047) were still not offered at that point: their request or result shapes are not yet established on this printer, and stock firmware offers no way to read a file's contents back at all. (The temperature setpoints (1028) were on that same not-offered list when this entry was written, because no ceiling for this printer had been established; they arrived afterwards with `cc2_set_temperature`, below.)

- Direct CC2 peripheral controls: `cc2_set_light` and `cc2_set_print_speed`. Both are two-phase like the job controls and the maintainer's Klipper MCP companion — without `confirm=true` a call only reads the printer and returns a preview carrying this call's own exact params, and no control command leaves the wire; with it, exactly one command is sent and never resent. `cc2_set_light` (1029) is the overhead light, on or off, and because the protocol doc's table (`brightness`) and the printer's own LAN web client and findings (`power` 1/0) disagree about the parameter, the command sends both spellings paired so they can never contradict each other, the same compatibility trick the Home Assistant integration uses; the light is binary, since no source shows it dimming. `cc2_set_print_speed` (1031) takes the printer's own discrete speed mode — 0 Silent (50%), 1 Balanced (100%, the default), 2 Sport (150%), 3 Ludicrous (200%) — and never a percentage: an out-of-range or percentage-shaped value refuses before a session is opened, naming the four. Each command is waited for 10 s, the longer of the two first-party windows (the official LAN client waits 5 s for these methods, the integration 10 s for every command). Accepted / refused / ambiguous are kept apart as elsewhere, and after an accepted or unanswered command one read-only look reports the light and mode the printer reports for itself, kept apart from acceptance — including when the two disagree, which is said out loud without earning a second command, and when the printer reported nothing, which stays unknown instead of becoming "off" or the default mode. `cc2_status` gained those two read-backs. The fan (1030) was still not offered at that point: the first-party sources disagree about the fan's scale, so it waits for evidence rather than a guess. (The temperature setpoints were held back in that same pass for the same kind of reason — no established ceiling — and they came afterwards, once Elegoo's own sources had been read for one: see `cc2_set_temperature`, below.)
- Direct CC2 job controls: `cc2_pause_print`, `cc2_resume_print` and `cc2_stop_print`. Each is two-phase like the maintainer's Klipper MCP companion — without `confirm=true` a call only reads the printer and returns a preview, and no control command leaves the wire; with it, exactly one command (pause 1021, stop 1022, resume 1023, no parameters) is sent and never resent. Waits follow the official Elegoo UI's own budgets (60 s pause/stop, 120 s resume): an accepted command is the printer's explicit `error_code` 0, a refusal keeps its code (1010 is the documented "no active print"), and a lost or unreadable answer is reported as ambiguous — never as a refusal — with at most one read-only status look after it. The printer is measured answering a resume only when the resume has completed (122 s once, outside the 120 s window), so an expired resume window says plainly that the print may well be resuming, and an accepted resume is never required to already report running. The three tools are declared like every other tool on the server; see *Changed* below for what that means for the old opt-ins.

### Fixed
- `cc2_list_files` can no longer report a page as a complete listing, and a file it withholds is now a file you can go and get. Before this, the tool asked the printer to certify the whole inventory — which it still does, and still refuses to do partially — and then put at most 200 names in the reply while reporting `complete: true` with the remainder counted in `total`. On a printer holding 201 files the 201st was real, certified, and unreachable: there was no argument that would fetch it. `offset` and `limit` are the fix and both are optional, so a caller who passes nothing gets what it always got: the first 200. What changed is what a truncated reply claims. `complete` is now true only of a reply that holds the whole listing itself; `inventory_complete` is the printer-side certification, which a page never weakens or inflates; `has_more`, `next_offset` and a note naming how many were left out say out loud what used to be a count with no way to act on it; and `limit` cannot be set above 200, because 200 is this server's own per-list reply cap and a limit of 500 that quietly came back as 200 would be the same hidden truncation with a number on it — so it refuses, names the cap and points at `offset`. A bad page argument (negative, fractional, a string, a boolean, `True` as an offset) is refused in-process before a session exists. Pinned by tests that walk 201 names across two pages and 460 names at 50 a page and require every name exactly once, that push a full 200-name page through the reply sanitiser and require all 200 to arrive, and that check the tool's JSON schema still documents both arguments.
- The reply sanitiser stopped rewriting the reply's own key names, which it did whenever the configured access code was short. The credential pass that makes a reply safe to hand a model ran over dictionary **keys** as well as their values, and that is right for a key a printer invented and wrong for a key this server wrote: the code is whatever the printer's LAN happens to use, and with the code `a` the keys `filename` and `state` arrived as `filen<redacted>me` and `st<redacted>te`, so a trusted reply carried keys no client had been told to expect. What is exempted is exact names, not substrings: `_CC2_REPLY_KEYS` is every key name this server and its `printer/cc2_*` adapters write, and `_cc2_key` returns one of those as it is and gives every other key the full pass — control characters, the 255-character cap and the credential replacement — so a short code still never comes back, in a key or a value, nor does one straddling a value's cap. The exemption is safe because a listed name is a string this source contains: the same key goes out whether the code is unset, set, or different, so an exempt key carries no fact about the secret, and the pathological case (a printer inventing a key that happens to equal a listed name) arrives as that name and nothing else. Two tests keep the list honest — one scans the adapters' dictionary literals and fails on any identifier-shaped name the list does not name, and one configures a one-letter code and requires every key of every read reply, including the error shape, to be a declared name — and both were checked to fail when a name is removed from the list.
- The words a caller pages by are `has_more`, and the tool, its over-cap refusal and the README now all say so. The reply keys above are one fix; the text written around them still told a reader to "keep calling with `offset=next_offset` until `complete` is true", and on a shelf that needed more than one page that never happens — `complete` belongs to the single reply that held the whole listing, so it is false on the last page exactly as on the middle ones, and a loop that obeyed that sentence read the shelf and then asked for the same last page forever. `complete` means exactly what it meant and `inventory_complete` is untouched; the stop condition is `has_more: false`, in the tool's own text, in the hint an over-large `limit` answers with, and in the README, with a test that walks 460 names at 200 a page along the walk those words describe and proves the last page ends the shelf without calling itself complete.
- The upload parser stopped refusing ordinary G-code for the spelling of a parameter letter. A file saying `M104 s140`, `M6211 s260 …` or `G180 s7` was refused for a lower-case `s`, although the same parser already matched the command word (`m104`), the tool select (`t0`), a compact heater code (`m109s240`) and a move's parameter letters (`g1 x1e6`) case-insensitively. Parameter letters now fold the same way, in one place. Only the letter folds: `M104 S140 s200` is still two setpoints and still refuses, as does a second numbered parameter of any spelling (`M104 s140 r200`), so no ambiguity check got looser on the way.
- `G0`, `G3`, `G4` and `M107` are on the upload command list, with their reasons written down, and nothing about the extrusion gate moved to let them in. `G0` and `G3` were already read as moves by this parser — their `E` parameter was already counted as an extrusion and already had to find an `M109` that waited at the temperature in force — so refusing them added no safety at all, and a test now proves both halves: `G0 E5`/`G3 E5` before any wait still refuse as cold extrusions, and after a verified wait they record their temperature exactly as `G1` does. `G4` (a dwell) and `M107` (the part fan's own off-switch, the equal of the already-allowed `M106 S0`) heat nothing and push nothing, and because their inertness is a claim about their *parameters*, the letters they may carry are written down: `G4 U255`, `M107 R200` and an `E` welded into either (`G4 P100E6`) refuse the file. What was *not* done is the part that would have been loose: no macro name joined the list, padded spellings (`G00`, `G0180`) still refuse as they always did, and the four real Centauri Carbon 2 slices this workflow has handled were re-checked as evidence of what the change can break: between them, 18.7 MB and 694,064 command lines, and not one `G0`, `G3`, `G4` or `M107` — the slicer profile for this machine writes `G1` for every travel — so no file that parsed before behaves differently now, and the mount slice still parses at 260 °C / 80 °C with its one verified extrusion temperature.

## [0.1.18] - 2026-11-02

### Fixed
- Claude Desktop could not connect: it showed the extension as failed with "connection is serving the 2026-07-28 protocol; the initialize handshake is not accepted" and no tools. The MCP SDK (2.2 and later) lets the first request on a stdio connection lock its protocol era, and a client that opens with a `server/discover` probe and then sends `initialize` on the same connection was refused. On stdio the server now answers a `server/discover` probe that arrives before any other request with METHOD_NOT_FOUND (-32601), the reply the specification tells clients to treat as "fall back to the handshake", so `initialize` opens the connection. Clients that only speak the handshake are unaffected, and clients in auto mode fall back as designed. Set `ORCA_MCP_PROTOCOL=auto` to hand the connection to the SDK untouched. Verified against Claude Desktop 4.4212 on macOS: its era probe, chat connection and local agent mode connection all complete the handshake and list the tools.
- `anyio` is now a declared dependency (the stdio transport imports it directly; before it arrived only through the MCP SDK).

## [0.1.17] - 2026-10-12

### Added
- Plate tools for fork v2.4.2-mcp.13 and later. `list_plates` shows each plate's index, name, lock state, build volume and objects, and which one is current. `add_plate` adds one. `select_plate` picks the plate that `slice_and_wait`, `get_gcode`, `render_plate` and `get_job_status` act on. `delete_plate` removes a plate; its objects are parked beside the bed and the reply counts them. `move_object_to_plate` keeps an object's position relative to its old plate, and an object parked beside the bed lands at the plate's centre. `list_objects` shows each object's plate. On an older build these tools say they need fork v2.4.2-mcp.13 or later.
- `arrange_plate` warns that with several plates it packs every unlocked plate together again.
- `transform_object` says that on fork v2.4.2-mcp.13 an object moved by coordinates joins the plate it lands on.

## [0.1.16] - 2026-10-09

### Fixed
- The printer tools no longer fail with a raw error when a printer sends a reply that can't be decoded, redirects, or isn't the JSON object expected at the top level. They return `protocol_error` (or `not_reachable` when the connection drops) with a message.
- An `ORCA_PRINTER_API_KEY` pasted with a trailing space or newline is trimmed before it is sent.
- A user name and password in the printer address are dropped from the address a message can echo, as a second guard after the existing redaction.
- Looking for the printer no longer leaves an HTTP client open when the call is cancelled or fails in an unexpected way.
- A damaged or hand-edited `printer.json` can no longer break a status call: the remembered address, protocol and time are checked when read, and the file is written in one atomic step.
- Errors from finding the printer (a bad `ORCA_PRINTER_URL`, a profile with no address, an unsupported connection type, OrcaSlicer not reachable) now carry a `printer` entry saying where the address came from.
- A printer address with port 0 is refused as not valid.
- While Klipper is starting up (right after a firmware restart, say), `get_printer_status` no longer shows 0 °C for the heaters and a warning count. It leaves the temperatures empty, because the sensors haven't been read yet, and the headline is "Klipper is starting up; check again in a minute."
- Console errors in the status lose Klipper's repeated restart instructions, as other Klipper messages already did, and an error that repeats shows once (its newest occurrence) instead of filling the list of five recent errors. A job's error message is trimmed the same way.
- Layer numbers in the job are always whole numbers or null. Text or a non-finite number from a printer no longer reaches the result.
- With OctoPrint, a job request that fails (or answers with something that isn't JSON) no longer fails the whole status. The status comes back with a note that the current job couldn't be read.
- `wait_for_printer` treats a job that completes successfully while it waits for `printing` or `first_layer_done` as met, instead of stopping with "The job ended before ...". A one-layer or very short print passes both points before the next poll. A cancelled or errored job still stops the wait early, and so does a job that was already complete when the wait began.
- `wait_for_printer` no longer sends a progress notification carrying an old status after a poll fails. The next notification comes with the next good poll.
- A hand-edited `printer.json` holding a remembered time no calendar can hold (`-1e300`, say) no longer puts a 310-character age in the "remembered printer" note. It reads "remembered earlier".
- `list_print_history` shows the failure reason already stored for a job, so the reply matches the row it just synced. Before, a reason read from the printer's console this time could differ from the one in the store.
- `list_print_history` reads a job's failure reason from the console the way the status does: Klipper's repeated restart instructions are cut, and a line with nothing else in it ("Printer is shutdown") is skipped. Before, that line could be stored as the reason, and a stored reason is not replaced later.
- `list_print_history` says what to do when the printer answers 404 for its history list: Moonraker versions before 0.9 need a `[history]` section in `moonraker.conf`, so add one and restart Moonraker. Before, it reported only the HTTP status.
- `list_print_history` copies jobs into the outcome store oldest first, as the always-on recorder does, so when one file was printed twice against a single saved slice, the earlier print claims it. The store writes also run off the event loop, so a busy store no longer stalls the server.
- When OrcaSlicer can't be read because of a setting other than the token (an invalid `ORCA_API_TIMEOUT`, say), the printer tools no longer tell you to check `ORCA_API_TOKEN`. The hint points at the server's OrcaSlicer settings (`ORCA_API_URL`, `ORCA_API_TIMEOUT`) and `detail` names the problem.
- `check_printer_match` no longer reports Klipper's `[firmware_retraction]` section as `absent` when retraction is off and Klipper's settings were never read. The printer side is empty then.
- `check_printer_match` says when OrcaSlicer didn't report the bed type, and its bed check is `unknown`, not `ok`, when the printable height or Klipper's Z travel wasn't available. The message says the height wasn't checked.
- `save_gcode` keeps the saved G-code file and returns `outcome_error` when recording the slice fails for any reason, not only a database or file error.
- An `ORCA_PRINTER_API_KEY` holding a character that can't be sent in an HTTP header (a curly quote pasted from a word processor, say) is refused with a `not_configured` message instead of a raw encoding error. The message never repeats the key.
- An OctoPrint reply that isn't a JSON object, and a Moonraker file-info reply that is the JSON value `null`, now return `protocol_error`. The first used to fail with a raw error (or, for `null`, read as offline or no job) and the second read as "no such file".
- With OctoPrint, a refused API key on the job request is reported as `auth_required` or `auth_rejected` like any other request, instead of becoming a note.
- The outcome store closes its database connection when it can't set up or upgrade the store (a locked or damaged file), instead of leaving it open for the caller.
- A printer error's extra detail can no longer replace its `error`, `message` or `hint`.
- A console error that is only Klipper's "Printer is shutdown" or "Printer is halted" line is no longer listed as a problem. The shutdown reason is reported on its own.

### Changed
- `get_printer_status` and `wait_for_printer` make one request fewer to a Klipper printer: the answer from the request that found the printer is reused once. Later polls of `wait_for_printer` still ask again.
- A printer found through OrcaSlicer's profile is tried first with the protocol that answered last time at the same address, so a new session makes fewer attempts.
- When a print that is already running is waiting for its heaters (OctoPrint reheating mid-print, or OctoPrint's first heat-up, which also shows file progress), the headline reads "Printing benchy: 28%, waiting for the heaters.", with the time left when it is known. A Klipper job's first heat-up still reads "Heating up to print benchy."
- The headline says "almost done" when no time is left or progress is 100 %, instead of "about 1 min left".
- `connected` in the status is false when the state is `offline`, OctoPrint keeps the job for a cancelled or errored print as Klipper does, and `headline` comes first in the result.
- The `list_print_history` summary reads "Your last 3 successful prints with an estimate ran 9% longer than estimated (median)." (or `shorter`, or `matched the estimate`). It no longer names OrcaSlicer, because the estimate can come from another slicer's file.
- `ended_at` in `list_print_history` carries the time zone offset, for example `2030-01-15T14:23+12:00`.
- `~/.orcaslicer-mcp/printer.json` is now created readable only by its owner.

### Documentation
- The README and the `wait_for_printer` text say that with OctoPrint, waiting for `printing` means waiting until the job is running with the heaters at temperature, because OctoPrint reports no extrusion.
- The README says the outcome store keeps a fingerprint of the objects' names and sizes, not their geometry, and `save_gcode` describes it the same way.
- The README says a finished print's row deleted from the store by hand comes back, without its saved slice settings, while its job is still in Moonraker's history, and that deleting the job there too drops it for good.
- The printer address setting in the Claude Desktop extension and the registry listing says a password in the address is stored as an ordinary setting, so the API key is the better choice.
- `list_print_history` and `recall_prints` say "the slicer's estimate", because an estimate can come from another slicer's file.
- The marketplace listing (`lhm.plugin.json`) now takes its tool descriptions from the live server with `scripts/gen_lhm_tools.py`, and a test keeps it from going stale. Before, many descriptions stopped mid-sentence or carried old `[needs M4b]` tags.

## [0.1.15] - 2026-10-09

### Added
- Printer feedback: `get_printer_status`, `wait_for_printer`, `list_print_history` and `check_printer_match`. The server finds the printer from OrcaSlicer's active printer profile, or `ORCA_PRINTER_URL`. Klipper (Moonraker) printers get all four tools; OctoPrint gets status and waiting, with `ORCA_PRINTER_API_KEY` when it needs a key. Read-only: no command, G-code or file is ever sent to the printer. The server only reads, with HTTP GET requests (carrying the API key, or the user name and password from `ORCA_PRINTER_URL`, when you set them). `wait_for_printer` also returns early when the job ends before the point it waits for, as when a print is cancelled while it heats. Requested in orcaslicer-mcp#12.
- The Claude Desktop extension has settings for the printer address, its API key and the printer name used in the outcome store.

### Changed
- `httpx` is now capped below 1.0. Its 1.0 pre-releases have no `AsyncClient`, so an install that resolved one (for example with pre-releases allowed) failed on the first printer or slicer call; the cap keeps a future 1.0 release from doing the same to fresh installs.
- The outcome store is now owned by this project (klipper-mcp carries a copy) and works without klipper-mcp. `save_gcode` always records the slice, with OrcaSlicer's time and filament estimates, and `list_print_history` adds finished prints with the printer's failure reason. New default location `~/.orcaslicer-mcp/outcomes/`; an existing `~/projects/_shared/print-outcomes/` is still used. The store upgrades itself in place by adding columns, so older versions can still read it.
- `recall_prints` rows include the failure reason and OrcaSlicer's estimates. `duration_s` is Moonraker's whole job time, including heating up and any pauses, so beside the estimates it overstates an overrun; `list_print_history` compares the print time, which leaves both out, with the estimate. `filament_g` is the G-code file's own estimate, because printers report filament in millimetres, not grams.
- A new outcome store's `printer_id` column defaults to `unknown`, the same value the store module uses when a caller passes no printer. Existing stores keep the default they were created with; every write names its printer anyway.

### Security
- `get_preset_config` could show part of a printer password to the model. It removed `user:password@` from `print_host` and `print_host_webui` only when the password had no `/` or space in it, so `http://user:pa/ss@host` came back unchanged. It now hides everything between the scheme and the last `@`, whatever the password contains. A URL with an `@` in its path also loses the part before that `@`, because it looks the same as a password with a `/` in it.

### Documentation
- README: the introduction, security notes and privacy policy now name the printer as the one other place the server connects to, read-only, and the data-retention entry lists the outcome store and `printer.json`.
- `docs/order-of-operations.md` explains why filament edits come before print edits on a multi-filament setup (per-filament keys are read merged but written to the one preset open in the Filament tab, and `select_preset` discards unsaved overrides in every group), with a recipe for setting up a multi-material plate. Linked from the README and from the `set_config` and `select_preset` docstrings.
- `set_config` warns against echoing a `get_config` value back for a per-filament setting (`hot_plate_temp`, `fan_min_speed`, `nozzle_temperature_initial_layer`, ...). `get_config` reports those merged across every loaded filament, while the write lands in the one filament preset open in the Filament tab, so the merged string corrupted that preset's list. Reported by @RoyPorter (orcaslicer-mcp#9); OrcaSlicer MCP v2.4.2-mcp.12 rejects the merged shape instead of storing it.
- `select_preset` says that it discards unsaved overrides in every preset group, not only the one being switched, and that newer slicer builds list the affected groups as `discarded_changes`. Reported by @RoyPorter (orcaslicer-mcp#10).

### Known issues
- `compare_settings` and `compare_slices` snapshot with `get_config` and restore with `set_config`, so for a per-filament key on a multi-filament setup the restore writes back the merged list. That never actually restored the original: it corrupted the filament preset the same way a manual write did. On OrcaSlicer MCP v2.4.2-mcp.12 and later the restore now fails loudly with `per_filament_length_mismatch` instead of corrupting silently; re-select the filament preset to recover. Making the snapshot/restore path per-filament aware is still to do.

## [0.1.14] - 2026-10-02

### Security
- Config writes that would change a key able to run code or drive the printer are refused with `blocked_by_local_policy` before they reach OrcaSlicer. They are `post_process`, every `*_gcode` template, `printer_model`, `printer_technology`, `filename_format`, and the printer connection settings (`print_host`, `print_host_webui`, `printhost_*`, `host_type`, `bbl_use_printhost`, `printer_agent`, `flashforge_serial_number`). This covers `set_config`, `apply_and_slice`, `edit_preset`, `compare_settings`, `compare_slices` and `set_object_config`. The fork's `PUT /config` accepts any preset key and `post_process` runs through the shell after export, so an assistant steered by injected text could otherwise save a command into a user preset. Thanks to @ferpa for the original change.
- Writing back an unchanged value passes, compared the way the fork serializes it (`true` is `1`). The host address and credentials are always refused, because OrcaSlicer never reports their current value.
- `edit_preset` checks against the named preset before selecting it, so a refusal no longer discards unsaved overrides. The `compare_*` snapshot restores skip the check, since they write back values just read from OrcaSlicer, so a restore never waits on an extra read.
- `ORCA_MCP_ALLOW_KEYS` opts specific keys back in. Wildcards such as `*_gcode` work, and the Claude Desktop extension exposes it as a setting. Names that match no protected key are logged at startup.
- `get_preset_config` hides `printhost_apikey`, `printhost_user` and `printhost_password`, and removes any `user:password@` from `print_host` and `print_host_webui`. The fork returns preset config unfiltered, unlike `GET /config`. Writes carrying the `<redacted>` placeholder are refused, so a round-tripped preset never overwrites a real credential.
- OrcaSlicer MCP v2.4.2-mcp.10 and later enforce the same rule inside the slicer, through Preferences → Remote API → Allow script, G-code and connection edits (off by default). When the slicer refuses a key, the tool reply carries a `hint` that says where the switch is.

### Documentation
- README: Windows fallback for `uvx` failing on `pywin32` with a sharing violation (pip venv, which retries). The same testing found the upstream 2.4.x "Profile syncing change" dialog and the fork's startup `remove_all` crash on a locked AppData datadir.
