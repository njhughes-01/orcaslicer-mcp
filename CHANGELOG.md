### Added
- **A CC2 upload now says whether the file's five machine-level G-code templates are still the stock ones, and its reply carries `printer_model`, `vendor_templates` and `templates_compared`.** The reason is an asymmetry nobody had said out loud: an uploaded file carries its own start, end, colour-change and layer-change G-code **inside its own config comments**, so the commands this parser refuses to read as macros are already sitting in the file as text — and whether they are still the ones Elegoo ships is a fact a person should see *on the upload*, not go and diff afterwards. The five are held verbatim in a new data module, `printer/cc2_stock_templates.py`, with a `SOURCE` constant naming the file they came from (the vendor's shipped CC2 machine profile at OrcaSlicer tag `v2.4.2`, with `before_layer_change_gcode` from the Elegoo machine-common profile at the same tag): copied out of the verbatim dump that had itself been checked blob by blob against both the installed 2.4.2 bundle on the Mac and the GitHub tag — 662 files, all matching — and generated into constants rather than retyped from memory or from a slice, with a verification run proving the constants byte-identical to that dump. Comparison is as loose as it can be without letting a line hide and exact everywhere else: the config value is one line with `\n` for every newline and `\\` for every literal backslash, exactly as Orca writes it, so it is unescaped first; then compared **line by line**, with trailing whitespace stripped on each line and trailing blank lines dropped on **both** sides, and every occurrence of a key in the file required to match. Why the tail alone is loose: the slicer writes the profile's own final newline one byte shorter into the config block than the dumped profile carries it (the reference two-tool slice ends its `machine_end_gcode` at `M84\n` where the dumped text has the line plus its newline), and no added or removed **line** can hide behind that difference — the first difference in the two line lists is the one reported. Everything else stays exact on purpose: the vendor's own `change_filament_gcode` begins with a blank line, so a leading blank line is compared rather than trimmed, and so is every inline comment. A key the file never wrote is **skipped, never guessed at**, and the count of what was actually looked at is reported beside the verdict as `templates_compared`, so `("stock", 0)` reads as "nothing was compared" rather than as "nothing was wrong" — which is the same reason this is a report and not a gate: a person who rewrote their own start G-code did that on purpose, and what they need to know is that this adapter's knowledge of a command's meaning does not extend to a template it has not read. So `compare_verdict` answers `"stock"` or `"modified: <key>, <key>"` and **nothing here ever refuses for it**; the parse computes it without a refusal path, `Cc2GcodeSettings` carries it, and `cc2_upload_gcode`'s reply carries all three names (`printer_model` is always the accepted value, because a file that named a different printer never reached a reply). The private receipt is deliberately **not** touched — no version bump, `to_dict` writes none of the three and `from_dict` never reads them, because they describe the upload that just ran and not the file sitting on the printer. Pinned by `tests/test_cc2_upload.py`: the reference two-tool fixture answers `("stock", 5)`; one extra line grafted into its `machine_end_gcode` answers `"modified: machine_end_gcode"` with the file still parsing (a report, not a refusal); a frame carrying none of the five answers `("stock", 0)`; and the frame whose templates are the trap ones answers `"modified: machine_start_gcode, change_filament_gcode"` with exactly 2 compared, which is the case that must never be read as a clean bill of health. No printer was contacted by any of it.
- **Multi-tool CC2 printing: `cc2_upload_gcode` and `cc2_start_print` now take a real multi-colour file (up to four tools) instead of refusing it.** A file's tools are the distinct `T<n>` numbers it selects, in first-seen order; the config keys OrcaSlicer writes per filament (`filament_type`, `nozzle_temperature`, `nozzle_temperature_initial_layer`) are now read one value per tool — `_config_value` splits on `;` as well as `,`, because Orca writes string lists with one and number lists with the other — and a per-filament list shorter than the file's highest tool refuses the file naming the key, while the plate/bed keys stay single (every tool shares the bed; a list that does not dedupe to one value refuses as before). The parser's flush rule is the reason this needed a design and not just a deletion: an `M6211` purge whose `R` differs from the verified wait used to refuse the file, and the vendor's own `change_filament_gcode` sets `R=[nozzle_temperature_range_high]`, so every multi-colour file Elegoo's slicer emits tripped it. `R` may now differ from the verified target only when it equals the declared `nozzle_temperature_range_high` of **both** the tool being left and the tool being switched to, read from the file's own config list and held inside the existing sanity fence, and it is then recorded as a **flush** temperature of both tools, apart from their printing temperatures (design amendment 9): a start reports a flush up to 10 °C over a mapped tray's rated maximum in a note — Elegoo's own PLA profile flushes at 240 °C while its catalog rates PLA trays to 230 °C — and refuses anything further over, because the upload bounds `R` only by the file's own declared range-high; a bare `T<n>` tool change with no `M6211` purge before it refuses outright; `Q` and `S` keep today's rule unchanged, a purge's `T` must still name a tool the file selects, and `M220` (the speed-factor override, `S` as its only parameter letter) joined the safe-command list because it scales the feedrates of moves already gated and commands no heater and no filament. The upload receipt is version 3: `Cc2UploadReceipt` gains `tools`, one entry per tool carrying its index, material, both nozzle temperatures and its extrusion temperatures, the flat `material`/`tool_index`/temperature fields stay the first tool's for readers that know only them, and `from_dict` reads a version-2 receipt as exactly one tool built from those flat fields and refuses anything else as before. At start, `tool_to_tray` is now 1–4 entries whose key set must equal the receipt's tool set exactly (a missing or extra tool refuses `tool_map_mismatch`, two tools on one tray refuses `tool_map`, both before anything is sent), every entry runs the existing per-tray presence/printability/material/temperature checks against **its own** tool, and the single 1020 then carries a `slot_map` of one complete `{t, canvas_id, tray_id}` entry per tool ordered by `t`, built from the trays that just answered — the shape Elegoo's own LAN client builds for a multi-colour print, byte-for-byte in the two keys this server sends. Every reply of a multi-tool start carries a note saying the honest thing: this adapter has never sent a multi-entry `slot_map` and has never observed this firmware's answer to one, so **whether the firmware honours it is unverified** and the note stands until a live test lands. Pinned by `tests/test_cc2_upload.py` (a fixture built from the head, one real T1 change block and the tail of a real two-colour slice: two PLA tools parsed with 240 in both extrusion lists, a range-high-below-R flush refusing while an R equal to the target still passing, `M220 S100` passing and `M220 X1` refusing, an unselected purge `T` still refusing, the `;` split, the short-list refusal, and a two-tool receipt round trip with a version-2 dict still reading as one tool), `tests/test_cc2_start.py` (the two-entry `slot_map` on the wire, missing tool, extra tool, shared tray and a tray rated below its tool's temperatures each refusing with nothing sent, all one-tool tests unchanged) and the tool layer in `tests/test_server_cc2.py` (`_cc2_tool_map` accepting one to four pairs and refusing five, a bad key and a non-dict with the `{"0": "1", "1": "2"}` example in every refusal, and the upload reply's `tools` list). No printer, network, port or credential was touched by any of this work, and nothing was committed, pushed, installed or deployed: every test is a scripted reply, and the live multi-colour print on Nathan's CC2 is recorded as open.
- Direct CC2 CANVAS tray filament-info write: `cc2_set_tray_filament` (method 2003, `SetFilamentInfo`) rewrites what one CANVAS tray says it holds, and it ships with the truest label available: **method 2003 has never been sent to a CC2 by anyone on this project, so every reply carries `verified_on_this_printer: false` beside the sentence saying why, and four questions about this firmware have no answer yet** — whether it answers 2003 at all, what it does with a `filament_code` or a brand it has never seen, whether its 2005 read reflects the change immediately (the auto-refill readback lagged), and whether it accepts a tray edit while a print runs. What the evidence chain establishes is the wire shape, and it is first-party: Elegoo's published LAN web client (`elegooofficial/elegoo-fdm-web`, release 20260625, a 3,605,472-byte `index.html` unpacked for this) spells `SetFilamentInfo = 2003` in the same method enum that names `SetAutoFillFilament = 2004` and `GetCanvasInfo = 2005`, treats a nonzero `error_code` as the failure it toasts as "Failed to set filament information.", and passes no timeout override for the method, so that request layer's 5 s default applies — the same pair of first-party windows as 2004, so the wait here is the longer of that and the integration's 10 s, and nothing is ever resent to catch a slow answer. The params are the nine fields the tray edit dialog builds (they appear verbatim, twice, in the bundle) and the slot page overwrites the ids from the page it was opened from before sending: `canvas_id`, `tray_id`, `brand`, `filament_type`, `filament_name`, `filament_code`, `filament_color`, `filament_min_temp`, `filament_max_temp` — nine fields, all sent every time, and **of those nine a human only ever supplies four** (which tray, which material, which colour, which brand): the dialog derives the type, the code and both temperatures from its lookup in the vendor's own 50-row filament catalog, so this tool embeds that same catalog (all 50 rows transcribed to `openspec/changes/cc2-tray-filament-info/filament-catalog.txt` and compiled into `printer/cc2_tray.py` so an installed server needs no checkout), takes no type, code or temperature as arguments at all, and treats a caller-supplied temperature as what it is — the guess the vendor UI never asks for. A name outside the catalog refuses **before any session opens**, listing the valid names in full, because that is not a pedantic bar but the vendor's own lookup answered with empty strings and a 0-0 range, which on this wire is a tray told it holds a material with no type, no code and no temperature — not a refusal the printer owes anyone. The colour is `#RRGGBB`, taken case-insensitively and sent upper-case; the brand is stripped, non-empty, at most 32 characters, free text allowed because the dialog allows free text — while the dialog itself offers only "ELEGOO" and "Generic", so anything beyond those two is allowed and labelled unproven against a printer by the reply's own `verified_on_this_printer`. The counter-evidence is recorded beside the evidence: the bundle the printer serves **itself** (`/webapp/lan/index.html`, firmware 02.01.00.00, 11,170,761 bytes) contains `SetFilamentInfo` **zero times** — that build still speaks the pre-CANVAS websocket name `CmdAMSSetFilamentInfo = 501` for the same idea — so what is proven is the current published client's frame and nothing about this firmware's behaviour, which is exactly why the live test (an idle printer, Nathan's yes for the write, one tray rewritten, the read-back recorded) is recorded as open and why a refusal out of this tool is worth recording as evidence about the firmware rather than read as a broken printer. The write/read asymmetry is pinned by tests because both spellings are correct on their own half of the wire: the write says `filament_min_temp`/`filament_max_temp` and carries `filament_code`, while the 2005 read answers `min_nozzle_temp`/`max_nozzle_temp` and never reports a code — no third spelling is invented. It is two-phase like every other control here — no `confirm=true`, no command: a preview call sends only the read-only 2005 and returns the exact nine-field 2003 params a confirmed call would send beside the printer's own words for what that tray holds right now — and **the gate is the machine-state read first and the roster read second on both phases**: the 1002 must call the printer idle for a job — printing, paused, initializing or any state the adapter cannot read refuses before anything else is asked, because an unreadable state is never an idle one — then the `(canvas_id, tray_id)` pair must appear in the printer's 2005 answer with its unit reporting connected, and a 2005 that will not answer **refuses** the change, the one deliberate difference from the auto-refill switch, because a tray write without a readable tray roster is a write to nowhere. There is an idle-machine gate, and it is this adapter's bar, not the vendor's: the dialog's load/unload buttons are gated by machine state while the edit icon that opens the dialog is not, so waiting for idle is a rule of ours — said out loud in the preview's and the accepted reply's `IDLE_GATE` note, with the very reading the gate stood on carried in the preview as its own field (`machine_now`: the printer's own state number and the documentation's word for it). Confirmed sends exactly one 2003, never resent; accepted (an explicit `error_code` 0) / refused (its code kept, and it earns no further read) / ambiguous (no answer, an unreadable one, or a dropped session) are kept apart with `cc2_control`'s vocabulary imported rather than reworded; and after an accepted or unanswered command one quiet read-only 2005 reports that tray's fields as a fact of its own, kept apart from acceptance, with a contradiction said out loud without earning a second command and the readback labelled as possibly lagging. Covered by `tests/test_cc2_tray.py` (152 tests: the catalog's 50 rows with three spot-checks against the vendor table — PLA `0x0000` 190-230, PETG `0x0100` 230-260, PPS-CF `0x0E01` 340-360 — every refusal, the colour and brand normalisation, the nine-field frame byte-for-byte, the idle gate in both phases (printing, paused and an unreadable 1002 each refusing with no 2003 on the wire), the preview sending `[1002, 2005]` only, the confirmed call `[1002, 2005, 2003, 2005]`, a refusal `[1002, 2005, 2003]` with no follow-up read, ambiguous never resent, unknown tray / disconnected unit / unreadable roster each refusing with no 2003 on the wire, the contradiction note, the note caps, `verified_on_this_printer` false everywhere, and no token or host string riding in any reply), plus the tool added to `tests/test_server_cc2.py` (the parameter bar at the tool layer before any session opens, the recorded preview and confirmed wire sequences, the input schema, the reply-key walk over every name the new module emits, and the tool in the default-posture and fresh-interpreter discovery probes), the annotation/open-world/roster tables, and `tests/test_cc2_filament.py`'s standing bar that keeps the withdrawn module name out of the roster, the README and the manifests. The roster went sixteen tools → seventeen, and the README, `lhm.plugin.json` (regenerated, never hand-edited) and the prose in `server.py` and `tests/test_server_cc2.py` were updated to say so, including the README's security bullet (which now counts ten of seventeen changing printer state and names the tray write among them) and the auto-refill entry's "2004 sits beside 2003" sentence, which now names the separate tool that 2003 has become here. No printer, Centauri Carbon 2, network, port, credential or environment file was touched by any of this work, and nothing was installed, committed, pushed or deployed: every test is a scripted reply, and nothing was sent to any machine.
- Direct CC2 camera picture: `cc2_camera_snapshot` returns **one frame** from the printer's own camera stream as an MCP image block with a summary line and its full sanitised metadata as text beside it, and it is the first tool on this server that reaches a CC2 **without speaking its protocol at all** — one plain-HTTP GET, no discovery, no MQTT session, no command, and none of the printer's roughly four client slots spent, so a picture still works when the roster is full. **What this deliberately does not do is ask the printer for the address**, and that is the whole design decision. The printer's own camera-address method (1042) remains an internal, unregistered candidate in `printer/cc2_camera.py` for the reason its own module spells out: no reply of it has ever been captured from this firmware, and the community manual and the Home Assistant integration built on it call that same method a **toggle** while Elegoo's own LAN client sends it parameterless on a button press — so sending it could switch a stream on or off, and nothing here proposes to settle that by sending it. That is a reason not to ask, not a reason to leave Nathan's camera unexposed, because the stream does not depend on the answer: the protocol manual describes the MJPEG stream on **port 8080**, answering every request whatever the path or query, unauthenticated and usually allowing a **single viewer**; that same integration, when the printer's method answers with no address, composes `http://<printer-ip>:8080/?action=stream` for itself out of its own `CC2_VIDEO_PORT`/`CC2_VIDEO_PATH`; and **Nathan has opened that exact stream on his own Centauri Carbon 2 repeatedly and captured images from it** (2026-11-06), which is the strongest evidence available here and the reason this shipped as a tool rather than as a candidate. Those three are evidence about the stream and nothing else: every reply carries `camera_method_sent: false`, `printer_advertised_url: false`, `stream_url_source: "composed_by_this_server"` and `verified_on_this_printer: false`, plus a warning saying a picture proves a stream answered and says nothing about that method in either direction, so the fetch neither proves nor disproves the toggle question and does not pretend to. The address is built from `ORCA_CC2_URL` and nothing else — **no printer address, including the lab's, appears in the adapter** (pinned by a test that scans the module and the test file for any internet-routable address and for the lab's own ranges) — and it goes through the transport's own `resolve_target` and a guard that demands an IP literal, so the picture is met at the very address the MQTT session is pinned to, with no resolver left between the policy decision and the socket, the same `_refusal` that gates MQTT refusing public/multicast/unspecified/link-local/broadcast, `trust_env=False` so no `HTTP_PROXY`/`NO_PROXY` in the environment can route a LAN camera fetch through a third machine, and `follow_redirects=False` so a 3xx is a refusal naming its status instead of a hop to an address this LAN policy never judged. Because a stream is by definition a reply that never ends, the fetch is bounded in four places and none of them is quiet: **one request, never a second one** after a timeout or a mid-stream failure (a stream that produced nothing may already have displaced another viewer, and nothing here is idempotent the way a request-only protocol pretends its reads are); a 10 s window enforced by `asyncio.timeout` so even a stream trickling one byte a second cannot outrun it; at most 8 MiB consumed hunting for a frame; and the kept frame capped at 2 MiB, the same ceiling `cc2_file_thumbnail` holds, refused with its size named and **never truncated** because half a JPEG is a corrupt picture. The frame hunt skips what a naive hunt gets wrong, and each case is a test: the tail of a frame the camera began before this server connected is dropped rather than reported as a truncated picture (so a snapshot is always a whole frame or an honest refusal), an `FF D8` whose next byte is not a marker that can open a frame is stepped over, `FF` fill bytes between markers do not move the length field, and — the case a first-`FF D9` search gets silently wrong — an EXIF `APP1` block can carry a nested thumbnail that ends with an end-of-image marker of its own, so the hunt walks the frame's segments by their declared lengths and finds the frame's real end instead of handing over its head — and it keeps walking past the **first** scan, because a multi-scan (progressive) frame redefines its tables and opens its next scans between its start and its end, and those payloads can carry `FF D9` bytes of their own. The stream is released exactly once on every path (success, over-size frame, marker-pair frame, non-200, redirect, stalled read, connection that never opened, mid-stream failure, self-closed stream, a chunk that is not bytes, the window expiring) and **including under cancellation**, which is the case an `async with` does not cover on its own and which is what would otherwise leave the printer believing a viewer is still watching; the close is shielded, so a caller cancelled mid-read still hands the camera back, and suppressed, so a failed cleanup never replaces the refusal it follows. Credentials are excluded by construction rather than filtered afterwards: the composed address has no authority for a login to live in (and the one guard that could see a login-bearing string withholds the whole string rather than quoting it), only one sanitised, control-character-stripped, 100-character `Content-Type` word is kept from the reply's headers, no other header value, no byte from before the frame and no exception's own sentence ever reaches a reply, and no authentication is sent at all — a camera that asks for a login gets `auth_rejected` with a sentence saying this server sent no credential and will not start. Two claims it refuses to make are said in the reply rather than discovered by a person: the manual's single-viewer limit means opening the stream may be refused or may displace whoever was watching, and this is the room the camera sees, not the print bed, with nothing here decoding or vouching for what is drawn in it. A review pass on 2026-11-07 found and fixed three defects in it, each with a test that reproduced it first: the tool built its metadata dict and **dropped it** on the way out, so the client saw a sentence instead of the claims the adapter made (it now returns the image, a summary line carrying the single-viewer warning, and the metadata as JSON, and the test asserts the content list the MCP client is actually handed, base64 included); the 8 MiB read ceiling was checked **after** a frame was accepted, so one oversized chunk containing a complete frame was kept from a hunt already past its number (the ceiling is now counted before a chunk is appended, which also bounds what the hunt can hold to the ceiling plus one chunk); and the hunt stopped at the first `FF D9` after the first start-of-scan, which cut a real multi-scan JPEG in half inside a later segment whose payload happened to hold an end-of-image (it now walks every scan, honouring each segment's declared length, and a marker that cannot follow a scan refuses the candidate instead of producing a corrupt frame). Covered by `tests/test_cc2_snapshot.py` (91 tests: the address follows the configuration and is never hardcoded, the transport's policy is what decides, no lookup happens for a literal, the frame hunt's traps including two-scan and three-scan frames with restart markers and an end-of-image embedded between them, one request per call on every path, the four caps each naming their number including a whole frame refused inside a chunk that breaches the read ceiling, the release counted on every path including a real task cancellation, no network touched with a literal configured, and the tool layer returning the image plus its warning and metadata — asserted through the server's own tool manager as the MCP-visible content — refusing in the shape every CC2 tool uses, and answering `not_configured`/`printer_contacted: false` with nothing contacted), plus the tool added to `tests/test_server_cc2.py`'s zero-network sweep and to its fresh-interpreter probe child (so the unconfigured refusal and the counted network zero are proven for the sixteenth tool as much as for the other fifteen), and the annotation/open-world/roster tables. The camera candidate's own posture tests were re-pinned rather than deleted: the camera is now exposed, and `printer/cc2_camera.py` is still not wired to anything — a test fails if any server code imports it or reaches its reader, and the names and the method number that must stay out of `server.py`, `README.md` and both manifests are still scanned for, so the 1042 candidate cannot drift into being advertised. The roster went fifteen tools → sixteen, and the README, `lhm.plugin.json` and the prose in `server.py` and `tests/test_server_cc2.py` were updated to say so, including the README's security bullet (which now names the camera fetch as plain HTTP on the camera port, once, unauthenticated, no proxy, no redirect) and the sentence that used to claim this MCP does not expose the camera stream at all, which is no longer true and now says exactly what is exposed (a picture) and what is not (camera control). No printer, Centauri Carbon 2, Home Assistant, Mac, network, port or credential was touched by any of this work, and nothing was installed, committed, pushed or deployed: every test is a scripted stream, and the live capture (Nathan's printer idle, the stream free of another viewer, one picture taken and looked at, and the single-viewer behaviour observed rather than assumed) is recorded as open in `openspec/changes/cc2-direct-print/revised-plan.md`.
- Direct CC2 CANVAS auto-refill switch: `cc2_set_auto_refill` (method 2004) turns the printer's auto-refill switch on or off with one boolean, and it is shipped as the labelled candidate it is: **one CC2 changed and restored the setting, but automatic refill during a print remains unverified, so every reply carries `verified_on_this_printer: false` beside a sentence naming why**, and the one thing that can move that label is a real print, which has not happened. What is established is first-party and narrow, and it is all this tool uses: Elegoo's own LAN web client, the bundle the printer serves itself, defines `SetAutoFillFilament = 2004` and `GetCanvasInfo = 2005` in its own method enum, sends `{method: 2004, params: {auto_refill: <the toggle's boolean>}}`, treats a nonzero `error_code` as the failure it shows as "Failed to set auto refill.", and paints the very same toggle from `canvas_info.auto_refill` of the 2005 reply — one field name on the way in and on the way out, which is why that field is the only thing this command ever carries. **The trap in this family is the older integration protocol manual, which spells the parameter `enable`,** both in its methods table and in its own worked example, while its own 2005 sample answers `auto_refill` and the integration that ships that manual defines the 2004 constant and never sends it. Unlike the light (1029), where the two documented spellings are paired in one command because both are attested, `enable` is never sent here in any combination: pairing an undocumented field because one table names it is how a printer gets told something no client of Elegoo's ever has, and that same manual's table makes the identical class of mistake on the delete command (`filename` where Elegoo's own client sends `file_path`), so a table row of that manual is not proof about this firmware. Because 2004 lives beside 2003 (which writes a tray's filament info) and the 2005 reply carries `active_canvas_id` and `active_tray_id` next to the flag, one field is also a safety property: a call here cannot move which tray the printer prints from, rename a spool or touch a slot map, and tests pin on the recorded wire that no other method — 2003, 2005 as a command, or any file, job or heater method — ever accompanies it. It is two-phase exactly like every other control here: without `confirm=true` a call sends only the read-only 2005 and previews what the printer says now and the exact one-field command a confirmed call would send; only an exact `confirm=true` sends it, once, waited for 10 s (Elegoo's client passes no override for this method, so that client's 5 s default applies, and the integration waits 10 s for every command — the longer is taken, and nothing is ever resent to catch a slow answer). Accepted (an explicit `error_code` 0 — the printer not refusing), refused (its code kept, and it earns no further read) and ambiguous (no answer, an unreadable one, or a dropped session) are kept apart with the job controls' own vocabulary, imported rather than reworded. The read-back deliberately does **not** reuse `cc2_state`'s canvas reader: a status line has to answer, so that reader defaults an absent `auto_refill` to false, and for a control's read-back an absent field is not a reading — so an absent field, a 2005 that was refused or never answered, and a value that cannot be read each stay unknown with whatever did arrive kept beside them, while the integers 0 and 1 read as the numbers they are (the integration's own CANVAS model records another Elegoo machine answering int 1 where its client expects a boolean). One deliberate difference from the light and the speed mode: a CANVAS read that answers nothing does not block the preview or the change, because a printer with no CANVAS attached is a legal state for a switch the printer stores for itself, and refusing a preview for that reason would be a barrier the plan forbids; it is reported as unknown with its reason instead. After an accepted or unanswered command exactly one read-only 2005 reports the flag as a fact of its own, and a look that contradicts the command the printer just accepted is said out loud without ever earning a second command. Covered by `tests/test_cc2_canvas.py` and the auto-refill section of `tests/test_server_cc2.py` (the parameter bar, the one-field wire shape, `enable` proven never to leave, the unknown-preserving read-back, accepted/refused/ambiguous, exactly-once on the recorded wire including a lost answer and a dead session, the note-length caps, both phases at the tool layer, and the tool in the default-posture and fresh-interpreter discovery probes). No printer, Home Assistant, Mac, network or credential was touched, and nothing was committed, pushed or deployed: every test is a scripted reply, and the live test (idle printer, a CANVAS with a spare tray, Nathan's yes for the switch, a print run to one empty tray, the setting restored) is recorded as open in `openspec/changes/cc2-direct-print/revised-plan.md`.
- Direct CC2 print history: `cc2_print_history` (method 1036) reads the prints the printer lists for itself, and it is the first read on this server whose **reply shape has never been captured from a real CC2**, so it is shipped labelled as the candidate it is rather than as a verified feature. What is established is first-party and narrow: Elegoo's own LAN web client — the one the printer serves — asks `{method: 1036}` with **no parameters at all**, waits 30 s for it at that one call site, treats a nonzero `error_code` as "Failed to get print history", and reads `history_task_list`, whose entries it reads as `task_id`, `task_name`, `begin_time`, `end_time`, `task_status` and the four `time_lapse_video_*` fields; its duration column subtracts `end_time` from `begin_time`, which is that client's own proof that both stamps are unix seconds, and its status column is painted from the app's own table (`0 other, 1 complete, 2 cancel, 3 cancel, 4 printing, 5 pause`, anything else "Unknow"). Every one of those is used as the client's, and labelled as such — the status number is always carried next to the app's word for it, because that table is an app's vocabulary rather than a protocol's and two of its numbers share a word, and no unit or meaning at all is claimed for the time-lapse numbers. What is *not* established is everything else, so the tool refuses instead of guessing: a reply with no `history_task_list`, a list that is not a list, and an entry that is not an object each refuse with their own reason, naming key names but never values, one request, nothing fitted afterwards — and **no reply is claimed to have been tested on hardware: every test is a scripted reply, and each successful reply carries `verified_on_this_printer: false` beside a sentence saying why.** Two traps are pinned by tests. The community protocol manual lists 1036 with `{"page": 1, "page_size": 10}`, and that row matches Elegoo's *cloud* ("RTM") history call — which paginates with `pageNumber`/`pageSize` and answers camelCase `taskList`/`totalTasks`, with its four time-lapse fields hard-filled to zero — so no paging key of any kind is ever sent here, none of the camelCase names is ever read, a cloud-shaped reply refuses with a reason of its own, and a `totalTasks` sitting beside a LAN list is never borrowed as the count that makes the list look self-accounting. And because the request carries no page size, the printer decides how long the answer is: the reply caps itself at 100 entries and then says so loudly (`truncated_in_reply`, both counts, a warning naming that it is not the whole history and that there is no next page to ask for, because 1038 removes history entries and this server does not send it), with the cap deliberately set under this server's own 200-per-list sanitiser cap so a truncation is always this tool's honest sentence and never a silently dropped row. `complete: true` is earned only when the printer's own `total` meets the entries it actually sent and nothing had to be dropped; a total above them, below them, unreadable or absent each get their own sentence, an unreadable total keeps the entries it could read rather than destroying them, and an empty list with no count says the only true thing available — that an empty history cannot be told apart from a firmware that keeps history somewhere else. Missing fields stay null *and* named in that entry's `not_reported`; `0` stays "not recorded" rather than becoming midnight 1970 or a zero-length print; a reversed pair of stamps earns no duration; and a stamp too large for seconds is reported as suspiciously milliseconds-shaped and left unconverted. Text over 255 characters is **withheld with its length named, never cut** — this server's own sanitiser caps strings at exactly that length, and a plausible-looking half name would be worse than no name, so the bound has to withhold before the reply is made safe (a 900-character name is proven never to reach the reply, not even its tail). Entries stay in the printer's own order, unsorted and un-de-duplicated, because the official app sorting them for its own table is that app's business. The one field that can carry a credential is handled: a time-lapse link with a login in its authority is withheld and only its presence reported, the same rule the transport applies to a printer address carrying a login. **1037 (one print's detail) and 1038 (deleting history) are omitted, not implemented and not advertised**: `GetHistoryTaskDetail` appears in Elegoo's entire 3.6 MB web bundle exactly twice, both in the enum that defines it, never called, so it has no published request, response or caller, and this server will not take a `uuid` from a live 1002 status frame and send it somewhere as a task handle. Covered by `tests/test_cc2_history.py` (82 tests) and the history section of `tests/test_server_cc2.py` (10 tests, including the parameterless wire shape, the candidate label, all four unreadable-reply shapes, the truncation, the withheld login-bearing link and the sanitiser-ceiling proof), plus the tool in the default-posture and fresh-interpreter discovery probes. No printer, Home Assistant, network or credential was touched, and nothing was committed, deployed or run against a machine.

### Changed
- **What a CC2 upload refuses changed on both ends of the file: it now refuses a G-code that was not sliced for a Centauri Carbon 2, and it stopped refusing two temperature steps the slicer writes itself.** Five things, all of them measured rather than assumed, and each one pinned in `tests/test_cc2_upload.py`. **(1) A printer-model gate.** The file's own `; printer_model =` config line must name this machine exactly, `Elegoo Centauri Carbon 2`, or the upload refuses with a new `printer_model` reason naming the value found or its absence — and this one was not theoretical: a Centauri 2 slice had been **accepted** by this parser, and it parses clean today only because the two profiles happen to share most of their command vocabulary. That is exactly the accident to stop relying on: every claim this allow list makes about what a command does was read from the **Carbon 2's** published firmware and `[g180]`/M6211 configuration, which the Centauri 2 is a different machine with different macros, so a file for it is a file whose commands nobody has read. The value is checked as one value, a missing line refuses the same way as an unequal one, and the receipt is untouched (no version bump — the gate lives at upload). **(2) The slicer's own layer-two step-up is no longer read as cold extrusion.** A bare `M104` that moves a nozzle already waited at one tool's declared `nozzle_temperature_initial_layer` to **that same tool's** declared `nozzle_temperature` keeps the wait armed, becomes the target, and is recorded as a verified extrusion temperature; any other bare `M104` revokes the wait exactly as it always did. Before, the generator's ordinary second-layer temperature change refused at the next extrusion — and this is emitted by stock presets, not just by edited ones: the 41 CC2-compatible stock filament presets were resolved through their inheritance chains and **Generic ABS @Elegoo Centauri (260 → 270 °C)**, **Generic ABS-CF (250 → 260 °C)** and Nathan's own `inland PLA @Elegoo Centauri 2- Copy` (220 → 225 °C) all step up, while every other stock preset has equal temperatures, which is why the fault stayed invisible. What makes the step acceptable is that both numbers are the file's own declared, per-tool, range-checked config and the nozzle is moving between two printing temperatures, not toward a cold one; the firmware's own `M109` already tolerates ±5 °C, and the receipt's claim about which temperatures extrusion ran at is still true because the new value is what the extrusion after it runs at. **(3) A colour change between two filaments at different temperatures parses.** At a wipe-tower change the slicer writes `M104 S<next>` and a `G1 E-2` **before** the `M6211`, so the old gate saw a new setpoint and a retract and refused: an `M104` naming another tool's declared `nozzle_temperature` now arms a **pending** setpoint, negative-`E` moves behind it pass under the wait still in force (a retract runs at the old, still-waited temperature and joins no temperature story), and **any forward extrusion before the purge still refuses**, naming the pending number and the purge that has to wait at it. The purge itself is then held to `Q` = the wait in force and `S` = that wait **or** the steady `nozzle_temperature` declared for the tool being switched to — not to the steady value alone, because the stock start block writes `Q`/`R`/`S` all equal to the initial-layer temperature and a steady-only rule would have refused the stock files and the layer-two frames above — with `R` keeping its range-high rule and its flush margin, and a flush quote that does not match the wait in force still deferring, fail-closed, under a pending change. After the purge the wait in force is `S`, the current tool is the purge's `T`, the pending setpoint is retired and `S` is recorded on that tool as its verified extrusion temperature; equal-temperature changes (the shape every real multi-colour file so far has had) take the identical path and produce identical numbers. A pending setpoint is retired by an `M109`, by `S0`, by any other `M104` and by the `G180 S9` unload, so nothing pending survives a line that changes what the nozzle is doing. **(4) `BED_MESH_CALIBRATE` no longer carries a verified wait across it.** The comment claiming it sets no nozzle target was a claim about a **binary-only** library whose own strings carry `M109 S140`, `M140`/`M190` and `G180` numbers that wait, so what it really heats is not established — the parser now drops the wait at that line and the next extrusion needs a fresh `M109`, which is exactly what the stock start template does (`BED_MESH_CALIBRATE`, `G28`, `M109 S<first layer>`), so stock files print on unchanged and a file that extrudes between a mesh and its `M109` refuses naming the mesh. **(5) Three texts that were wrong, not just thin.** The purge refusal said "thirteen" letters where the firmware reads fourteen (the set really is `T Q R S A` plus `K L M N I J P C D`); the `G180` comment said the dispatcher loads `S1…S998` where `S998` can never be selected, so it now says `S1–S997`; and the `M600` refusal said only "unread", which under-sold it — `M600` stays refused, and the hint now says why a human should want it refused: on this firmware it is a filament-change pause that runs its load macro and an `M109` whose temperature **defaults to 250 °C**, a wait at a setpoint the file never commands, so a 210 °C PLA print paused for a colour change would be held at 250. Every refusal that existed before this change still exists — `M600`, `M141`/`M191`, `G10`/`G11`, `EXCLUDE_OBJECT_*`, `G17`, `SET_INPUT_SHAPER` and `M82` all still refuse, and no macro name joined the list. **(6) Every `cc2_start_print` reply now carries the tray-table note**, accepted, refused or ambiguous alike, because it is a property of the firmware rather than of one call: a bare `T<n>` has **no handler at all** on this firmware and the physical tray is chosen inside `M6211` from the printer's own persistent colour table, which no method this adapter speaks can read, so the `slot_map` sent is the mapping Elegoo's own client sends and the printer's table may override it — the same sentence now sits in the tool's own description and the module docstring, so a model reading the tool list learns it before it sends a start rather than after. Tests: fifteen new in `tests/test_cc2_upload.py` — the model gate naming a wrong value and naming its absence, the mesh reset refusing the extrusion after it beside the stock mesh→home→wait order still parsing, the layer-two step-up keeping the wait beside an undeclared step still needing a matching `M109` and the transition firing only for the tool in force, the mixed-temperature change parsing with the purge's waited `S` recorded beside its two refusals (a `Q` that is not the wait in force, and a forward extrusion between the tower's `M104` and its purge), the template verdict on four frames, and a test that the untouched two-tool fixture still parses **tuple for tuple** as it did before, which is the guard against a loosening that quietly changed what a good file means; that suite runs 305 passed. **The full suite is not green on this tree and says why**: `tests/test_server_cc2.py` carries 6 failures that predate this work and are logged as *Found* lines in `openspec/changes/cc2-stock-profile-allowlist/tasks.md` — its inline upload G-code carries no `printer_model` line, so the new gate refuses its five upload tests, and five template key names are missing from `_CC2_REPLY_KEYS` — both in files this task does not name, and each was verified failing identically with these edits stashed. `lhm.plugin.json` was regenerated from the live tool text (never hand-edited). No printer was contacted; every test is a scripted reply.
- **What a CC2 upload and start refuse, and what their replies carry, changed for multi-tool files.** Four refusals became accepts: a file that selects more than one tool, a purge `T` naming any selected tool (the rule itself is unchanged — it must still name a tool the file selects — only "the one tool" became "any of the tools"), an `M6211` `R` that equals both tools' declared range-high (see the *Added* entry beside this one for the rule), and `M220 S`. Three things that used to pass now refuse or are newly checked: `tool_to_tray` must cover exactly the receipt's tools (`tool_map_mismatch`) instead of taking exactly one pair, two tools mapped to one tray refuses (`tool_map`), and each mapped tray is now checked against its own tool's material and temperatures rather than the file's single set. The receipt format moved to version 3 (a version-2 receipt still reads, as one tool; anything else refuses as before), `cc2_upload_gcode`'s reply gained `tools` beside the existing first-tool fields, and a multi-tool start's reply carries the standing note that a multi-entry `slot_map` has never been sent by this adapter — so no reply here claims the firmware honours it. The module docstrings and the two tool descriptions now describe tools-as-selected rather than "exactly one tool", and the `lhm.plugin.json` tool listing was regenerated from the live tool text (never hand-edited).
- **The fifteen direct CC2 tools now share one registered MQTT session per server process instead of opening one each.** This is a fix for a fault that looked like the printer misbehaving: on a real Centauri Carbon 2, a run of four ordinary tool calls — status, list, a preview, one more — came back with `too_many_clients` from a printer that was idle, healthy and printing nothing. The CC2 speaks from its own broker, that broker takes **about four clients**, and the printer reaps a client that has gone on its own clock, so a session opened, used for one read and closed still occupied one of the four for a while: four calls of our own were enough to fill the roster, and then the printer refused us, and every refusal paid another registration to clean up. The only remedy the refusal could offer was "close other clients and wait", which is a person doing an agent's bookkeeping. So the tools borrow one session now (`printer/cc2_pool.py`): the first call registers it, the rest use it, and the heartbeat that keeps the printer from timing us out runs once for all of them. **Only the opening is serialised** — two calls that arrive at the same moment cannot register twice, the second waits for the open already in flight and shares what it gets — while requests on an established session run side by side, because the transport already matches every answer to the request id this server stamps on the wire, which is what makes sharing safe at all. A session the transport reports dead, or one the configuration left behind, is **retired and the next call opens afresh**: that repeats no command, because the pool sends nothing itself, and an unanswered command stays exactly as ambiguous as the reply that reported it said it was — no sleeping, no retrying, no second attempt to catch a busy printer, all of which this server has always refused to do. What ends a session is its own death, a configuration that moved (the address or the access code, re-read on every borrow, so re-pointing the server cannot leave a tool talking to the printer it was configured for), an idle window with nobody holding it, or the server's own exit — and **the idle window is this server's policy, not a protocol fact**: with nothing holding it the session closes after two minutes so a printer you have finished with gets its slot back, and the exit closes it too rather than leaving a client the printer has to time out on its own. A configuration this pool cannot read borrows nothing and opens nothing, and is not treated as evidence about a session it has not touched. Two safety details are worth stating plainly: a session is never closed out from under a caller using it (a retired one closes when that caller's own release lands, and a cancelled caller still gives its hold back), and the credential is handled no more loosely than before — the pool's identity key for a session is the address plus a **salted one-way digest** of the access code with a per-process salt, so it can notice a code that changed without holding a copy of it, appears in no reply, log, message or `repr`, and the code itself stays only in memory for exactly as long as the MQTT client beside it already held it. **What is not shared is anything across processes**: two MCP server processes — two agents, or an agent plus your own script — are two clients each holding a slot, and the printer's roster stays the limit; this stops one process from being several clients to a printer it is already talking to. Proven at both layers and on a real client: `tests/test_cc2_pool.py` (26 tests over a scripted session — one registration for a run of calls, concurrent callers getting their own answers and one wire frame each, a dead or closed session never lent again, both configuration changes, a failed open leaving nothing to borrow and never retried inside the call, cancellation, the idle window both ways, shutdown with and without a caller in flight, and the credential rule), a new section of `tests/test_server_cc2.py` (nine new tests at the layer the calls arrive at, 171 in the file), including a four-call run that registers once, two simultaneous calls that wait for one open, a session replaced by the very next call, an upload after another call still authenticating with the credential that session was met with, and the server's exit closing the session — including the exit where stdio failed), and the loopback test `tests/test_cc2_transport_mqtt.py` runs the pool against **real `aiomqtt`/paho on a stub broker**, where four requests over two borrows are one CONNECT, one registration, one subscription pair, four distinct ids and one DISCONNECT — a proof only a broker that counts clients can give. No printer, Home Assistant, Mac, network beyond loopback or credential was touched, and nothing was committed, pushed, installed or deployed.
- The peripheral read-back says what its timing is. `cc2_set_light` and `cc2_set_print_speed` take their one confirming look **straight after** the command, and nothing measured on any CC2 says how soon this printer's status reflects one — so both the accepted reply and the disagreement reply now say the look is immediate and can be the status lagging, with `cc2_status` named as the way to ask again. A wording fix, not a new read: still exactly one look, never a second command, never a wait or a poll, with accepted and observed kept as separate facts neither overwrites. Describing this server's own timing is the honest version of a caveat nobody has data for, because the timing is the one thing here that is actually known. Every note still fits the reply cap the sanitiser enforces, pinned by a test that fails if the caveat were cut off the end of a long note.
- The direct CC2 tools no longer hide behind `ORCA_CC2_READ` and `ORCA_CC2_WRITE`, and both variables are gone. Configuring the printer is the only opt-in there is: `cc2_status`, `cc2_list_files`, `cc2_upload_gcode`, `cc2_start_print`, `cc2_pause_print`, `cc2_resume_print` and `cc2_stop_print` are listed by any server, exactly like every other tool, whether or not a printer is configured. What changed is discovery, not reach: with no `ORCA_CC2_URL` set, every one of these tools still refuses, honestly and in this process, with `not_configured` and `printer_contacted: false`, before any name is looked up and before any socket is opened, and an address that carries a login or points somewhere public is refused the same way without echoing it. `ORCA_CC2_URL` and the access-code variables keep working as before, and so does every non-CC2 tool.

### Added
- Direct CC2 temperature control: `cc2_set_temperature` (method 1028) sets **one** heater's target — `extruder` (the nozzle, also read as `nozzle`) or `heater_bed` (also `bed`), one heater per command, the two frames Elegoo's own LAN control sends — and it is two-phase like every other control here: without `confirm=true` a call only reads the printer and previews the exact one-heater command and the ceiling it enforced, and no command leaves the wire. The point of this entry is where the numbers come from, because a heater tool that guesses is a hazard: **the ceiling is the input bounds of Elegoo's own official LAN control for this printer — 0-350 for the nozzle and 0-110 for the heated bed** (its web client, release 20260625, whose input handler clamps a typed number into them before it sends), and every reply carries the bound with that source named beside it and the words "not a hardware rating", because that is exactly what it is. Nothing else in the sources was usable as a limit and none of it was quietly adopted: the firmware's own `max_temp` from Elegoo's published CC2 config (600 extruder, 125 bed) is a sensor envelope that Elegoo's `heaters.cpp` refuses outside, which is a safety window rather than a target; the same Elegoo SDK's capability row records 300 for that extruder and 120 for that bed while binding those five values against a struct whose field order turns them into "minimum 300, maximum 1", so the row contradicts itself; and the official Elegoo profile bundle for this machine carries **no temperature-ceiling key of any kind**, which is the plainest possible reason why a slicer profile's nozzle or bed number is a print setting and can never be read as a machine limit for other filaments or nozzles. So the tool refuses above its sourced ceiling and **offers no parameter to raise it** — a caller-supplied "verified limit" argument would be the guess dressed up as an input — while any lower number is always open. A nozzle setpoint above the 300 the other Elegoo source names is sent, because the machine's own control reaches that high, with a note saying the two sources disagree and nothing claiming the printer is rated for it. `'chamber'` refuses before a session opens (its official control row is not editable and the published firmware config gives the box a sensor with no heater), as does anything that is not one of the two heaters, a setpoint that is not a number, or a number outside 0 to that heater's own ceiling — 320 is legal for the nozzle and illegal for the bed, because the ceilings are per heater and no single number was assumed. `0` is legal and is labelled for what it is: a heater turning off, the same thing this printer's own end-of-print G-code sends. One 1028 command per call, sent once and never resent, waited for 10 s (the longer of the LAN client's 5 s default for this method and the integration's 10 s for every command); accepted / refused / ambiguous are kept apart exactly as the job and peripheral controls keep them, a lost answer is never a refusal and never earns a resend, and after an accepted or unanswered command exactly one read-only look reports both the target and the actual temperature the printer states, kept apart from acceptance: a target still climbing is never read as a failure, an absent field stays unknown rather than becoming zero, and a target stated as anything other than the number just accepted (past a stated half-degree) is said out loud without earning a second command. Found in Elegoo's own sources, and pinned by `tests/test_cc2_temperature.py` and the temperature section of `tests/test_server_cc2.py` (mocked only: no printer was contacted, and the ceiling is a documented bound, not something probed by sending an out-of-range value, which the plan forbids).
- Direct CC2 information reads: `cc2_printer_info`, `cc2_file_detail` and `cc2_file_thumbnail`. All three are reads, each one request asked exactly once, and they fill the three questions the status frame cannot answer. `cc2_printer_info` (method 1001, no parameters) is what the printer says it is — model, its own name, serial, firmware/hardware/protocol versions, build volume and resolution, network type, remaining memory, camera and USB attachment — and it is the only place this server reads a firmware version from. `cc2_file_detail` (1046) is one file on the printer: size, total layers, the slicer's estimated time and filament, when it was created, how often and when last it printed, and its colours per tool, in the same words `cc2_list_files` already uses for those same facts. `cc2_file_thumbnail` (1045) returns the printer's own embedded preview for a file as an MCP image with one line of text beside it. None of the three invents a field: everything the printer did not answer is null and named again in `not_reported` (this firmware is measured answering two of its three version strings empty, and an empty string is not a version), the attributes reply carries the printer's `ip` and `mac` nowhere, and it says so plainly when the serial in the reply is not the serial the session pinned. Three ways a reply can be unhelpful are said instead of smoothed: a layer count that arrives under two field names with two different numbers is reported as both with the name that was used, a detail reply about a different file than the one asked for is reported as that, and a printer that answers none of a method's documented fields is refused rather than reported as an empty profile. Two wire facts are pinned by tests because they are the trap of this family: 1046 is sent `filename` and 1045 is sent `file_name`, so the two file reads are not interchangeable, and only `local` storage is ever asked for — the removable volumes are spelled two different ways by the two first-party sources and have never been offered to this firmware, so those spellings refuse instead of being guessed. A file name is held to the bar `cc2_list_files` prints by (no path, no control characters, at most 255 characters) and refuses before a session is opened, so these tools cannot be used to poke above the printer's own file store. The thumbnail is decoded, typed by its bytes' own signature rather than by the manual's \"typically PNG\", and bounded: an image over 2 MiB is refused with its size named and never truncated, because a half an image is a corrupt image and the image rides inside one tool reply. The fan (1030), the print history (1036/1037), the camera (1042) and file deletion (1047) were still not offered at that point: their request or result shapes are not yet established on this printer, and stock firmware offers no way to read a file's contents back at all. (The temperature setpoints (1028) were on that same not-offered list when this entry was written, because no ceiling for this printer had been established; they arrived afterwards with `cc2_set_temperature`, below.)

- Direct CC2 peripheral controls: `cc2_set_light` and `cc2_set_print_speed`. Both are two-phase like the job controls and the maintainer's Klipper MCP companion — without `confirm=true` a call only reads the printer and returns a preview carrying this call's own exact params, and no control command leaves the wire; with it, exactly one command is sent and never resent. `cc2_set_light` (1029) is the overhead light, on or off, and because the protocol doc's table (`brightness`) and the printer's own LAN web client and findings (`power` 1/0) disagree about the parameter, the command sends both spellings paired so they can never contradict each other, the same compatibility trick the Home Assistant integration uses; the light is binary, since no source shows it dimming. `cc2_set_print_speed` (1031) takes the printer's own discrete speed mode — 0 Silent (50%), 1 Balanced (100%, the default), 2 Sport (150%), 3 Ludicrous (200%) — and never a percentage: an out-of-range or percentage-shaped value refuses before a session is opened, naming the four. Each command is waited for 10 s, the longer of the two first-party windows (the official LAN client waits 5 s for these methods, the integration 10 s for every command). Accepted / refused / ambiguous are kept apart as elsewhere, and after an accepted or unanswered command one read-only look reports the light and mode the printer reports for itself, kept apart from acceptance — including when the two disagree, which is said out loud without earning a second command, and when the printer reported nothing, which stays unknown instead of becoming "off" or the default mode. `cc2_status` gained those two read-backs. The fan (1030) was still not offered at that point: the first-party sources disagree about the fan's scale, so it waits for evidence rather than a guess. (The temperature setpoints were held back in that same pass for the same kind of reason — no established ceiling — and they came afterwards, once Elegoo's own sources had been read for one: see `cc2_set_temperature`, below.)
- Direct CC2 job controls: `cc2_pause_print`, `cc2_resume_print` and `cc2_stop_print`. Each is two-phase like the maintainer's Klipper MCP companion — without `confirm=true` a call only reads the printer and returns a preview, and no control command leaves the wire; with it, exactly one command (pause 1021, stop 1022, resume 1023, no parameters) is sent and never resent. Waits follow the official Elegoo UI's own budgets (60 s pause/stop, 120 s resume): an accepted command is the printer's explicit `error_code` 0, a refusal keeps its code (1010 is the documented "no active print"), and a lost or unreadable answer is reported as ambiguous — never as a refusal — with at most one read-only status look after it. The printer is measured answering a resume only when the resume has completed (122 s once, outside the 120 s window), so an expired resume window says plainly that the print may well be resuming, and an accepted resume is never required to already report running. The three tools are declared like every other tool on the server; see *Changed* below for what that means for the old opt-ins.

### Fixed
- **Two review findings on the round-three attribution work: the closing plate read was skipped on a one-plate project, and a plate that *stopped* naming its copies between the two reads was treated as a plate that had not changed.** Both are holes in the same window, and the entry below describes the work they are found against. **(1) A one-plate project was not bracketed.** `save_gcode` and `recall_prints` asked for `/api/v1/plates` a second time only when the first reply said there was more than one plate, on the reasoning that the closing read exists to catch a plate being clicked and a project with one plate has nothing to click to. - With OctoPrint, a job request that fails (or answers with something that isn't JSON) no longer fails the whole status. The status comes back with a note that the current job couldn't be read.
- `wait_for_printer` treats a job that completes successfully while it waits for `printing` or `first_layer_done` as met, instead of stopping with "The job ended before ...". A one-layer or very short print passes both points before the next poll. A cancelled or errored job still stops the wait early, and so does a job that was already complete when the wait began.
- `wait_for_printer` no longer sends a progress notification carrying an old status after a poll fails. The next notification comes with the next good poll.
- A hand-edited `printer.json` holding a remembered time no calendar can hold (`-1e300`, say) no longer puts a 310-character age in the "remembered printer" note. It reads "remembered earlier".
- `list_print_history` shows the failure reason already stored for a job, so the reply matches the row it just synced. Before, a reason read from the printer's console this time could differ from the one in the store.
- `list_print_history` reads a job's failure reason from the console the way the status does: Klipper's repeated restart instructions are cut, and a line with nothing else in it ("Printer is shutdown") is skipped. Before, that line could be stored as the reason, and a stored reason is not replaced later.
- `list_print_history` says what to do when the printer answers 404 for its history list: Moonraker versions before 0.9 need a `[history]` section in `moonraker.conf`, so add one and restart Moonraker. Before, it reported only the HTTP status.
- `list_print_history` copies jobs into the outcome store oldest first, as the always-on recorder does, so when one file was printed twice against a single saved slice, the earlier print claims it. The store writes also run off the event loop, so a busy store no longer stalls the server.
- When OrcaSlicer can't be read because of a setting other than the token (an invalid `ORCA_API_TIMEOUT`, say), the printer tools no longer tell you to check `ORCA_API_TOKEN`. The hint points at the server's OrcaSlicer settings (`ORCA_API_URL`, `ORCA_API_TIMEOUT`) and `detail` names the problem.
- `check_printer_match` no longer reports Klipper's `[firmware_retraction]` section as `absent` when retraction is off and Klipper's settings were never read. The printer side is empty then.
- `check_printer_match` says when OrcaSlicer didn't report the bed type, and its bed check is `unknown`, not `ok`, when the printable height or Klipper's Z travel wasn't available. The message says the height wasn't checked.
- `save_gcode` keeps the saved G-code file and returns `outcome_error` when recording the slice fails for any reason, not only a database or file error.
- An `ORCA_PRINTER_API_KEY` holding a character that can't be sent in an HTTP header (a curly quote pasted from a word processor, say) is refused with a `not_configured` message instead of a raw encoding error. The message never repeats the key.
- An OctoPrint reply that isn't a JSON object, and a Moonraker file-info reply that is the JSON value `null`, now return `protocol_error`. The first used to fail with a raw error (or, for `null`, read as offline or no job) and the second read as "no such file".
- With OctoPrint, a refused API key on the job request is reported as `auth_required` or `auth_rejected` like any other request, instead of becoming a note.
- The outcome store closes its database connection when it can't set up or upgrade the store (a locked or damaged file), instead of leaving it open for the caller.
- A printer error's extra detail can no longer replace its `error`, `message` or `hint`.
- A console error that is only Klipper's "Printer is shutdown" or "Printer is halted" line is no longer listed as a problem. The shutdown reason is reported on its own.

### Changed
- `get_printer_status` and `wait_for_printer` make one request fewer to a Klipper printer: the answer from the request that found the printer is reused once. Later polls of `wait_for_printer` still ask again.
- A printer found through OrcaSlicer's profile is tried first with the protocol that answered last time at the same address, so a new session makes fewer attempts.
- When a print that is already running is waiting for its heaters (OctoPrint reheating mid-print, or OctoPrint's first heat-up, which also shows file progress), the headline reads "Printing benchy: 28%, waiting for the heaters.", with the time left when it is known. A Klipper job's first heat-up still reads "Heating up to print benchy."
- The headline says "almost done" when no time is left or progress is 100 %, instead of "about 1 min left".
- `connected` in the status is false when the state is `offline`, OctoPrint keeps the job for a cancelled or errored print as Klipper does, and `headline` comes first in the result.
- The `list_print_history` summary reads "Your last 3 successful prints with an estimate ran 9% longer than estimated (median)." (or `shorter`, or `matched the estimate`). It no longer names OrcaSlicer, because the estimate can come from another slicer's file.
- `ended_at` in `list_print_history` carries the time zone offset, for example `2030-01-15T14:23+12:00`.
- `~/.orcaslicer-mcp/printer.json` is now created readable only by its owner.

### Documentation
- The README and the `wait_for_printer` text say that with OctoPrint, waiting for `printing` means waiting until the job is running with the heaters at temperature, because OctoPrint reports no extrusion.
- The README says the outcome store keeps a fingerprint of the objects' names and sizes, not their geometry, and `save_gcode` describes it the same way.
- The README says a finished print's row deleted from the store by hand comes back, without its saved slice settings, while its job is still in Moonraker's history, and that deleting the job there too drops it for good.
- The printer address setting in the Claude Desktop extension and the registry listing says a password in the address is stored as an ordinary setting, so the API key is the better choice.
- `list_print_history` and `recall_prints` say "the slicer's estimate", because an estimate can come from another slicer's file.
- The marketplace listing (`lhm.plugin.json`) now takes its tool descriptions from the live server with `scripts/gen_lhm_tools.py`, and a test keeps it from going stale. Before, many descriptions stopped mid-sentence or carried old `[needs M4b]` tags.

## [0.1.15] - 2026-10-09

### Added
- Printer feedback: `get_printer_status`, `wait_for_printer`, `list_print_history` and `check_printer_match`. The server finds the printer from OrcaSlicer's active printer profile, or `ORCA_PRINTER_URL`. Klipper (Moonraker) printers get all four tools; OctoPrint gets status and waiting, with `ORCA_PRINTER_API_KEY` when it needs a key. Read-only: no command, G-code or file is ever sent to the printer. The server only reads, with HTTP GET requests (carrying the API key, or the user name and password from `ORCA_PRINTER_URL`, when you set them). `wait_for_printer` also returns early when the job ends before the point it waits for, as when a print is cancelled while it heats. Requested in orcaslicer-mcp#12.
- The Claude Desktop extension has settings for the printer address, its API key and the printer name used in the outcome store.

### Changed
- `httpx` is now capped below 1.0. Its 1.0 pre-releases have no `AsyncClient`, so an install that resolved one (for example with pre-releases allowed) failed on the first printer or slicer call; the cap keeps a future 1.0 release from doing the same to fresh installs.
- The outcome store is now owned by this project (klipper-mcp carries a copy) and works without klipper-mcp. `save_gcode` always records the slice, with OrcaSlicer's time and filament estimates, and `list_print_history` adds finished prints with the printer's failure reason. New default location `~/.orcaslicer-mcp/outcomes/`; an existing `~/projects/_shared/print-outcomes/` is still used. The store upgrades itself in place by adding columns, so older versions can still read it.
- `recall_prints` rows include the failure reason and OrcaSlicer's estimates. `duration_s` is Moonraker's whole job time, including heating up and any pauses, so beside the estimates it overstates an overrun; `list_print_history` compares the print time, which leaves both out, with the estimate. `filament_g` is the G-code file's own estimate, because printers report filament in millimetres, not grams.
- A new outcome store's `printer_id` column defaults to `unknown`, the same value the store module uses when a caller passes no printer. Existing stores keep the default they were created with; every write names its printer anyway.

### Security
- `get_preset_config` could show part of a printer password to the model. It removed `user:password@` from `print_host` and `print_host_webui` only when the password had no `/` or space in it, so `http://user:pa/ss@host` came back unchanged. It now hides everything between the scheme and the last `@`, whatever the password contains. A URL with an `@` in its path also loses the part before that `@`, because it looks the same as a password with a `/` in it.

### Documentation
- README: the introduction, security notes and privacy policy now name the printer as the one other place the server connects to, read-only, and the data-retention entry lists the outcome store and `printer.json`.
- `docs/order-of-operations.md` explains why filament edits come before print edits on a multi-filament setup (per-filament keys are read merged but written to the one preset open in the Filament tab, and `select_preset` discards unsaved overrides in every group), with a recipe for setting up a multi-material plate. Linked from the README and from the `set_config` and `select_preset` docstrings.
- `set_config` warns against echoing a `get_config` value back for a per-filament setting (`hot_plate_temp`, `fan_min_speed`, `nozzle_temperature_initial_layer`, ...). `get_config` reports those merged across every loaded filament, while the write lands in the one filament preset open in the Filament tab, so the merged string corrupted that preset's list. Reported by @RoyPorter (orcaslicer-mcp#9); OrcaSlicer MCP v2.4.2-mcp.12 rejects the merged shape instead of storing it.
- `select_preset` says that it discards unsaved overrides in every preset group, not only the one being switched, and that newer slicer builds list the affected groups as `discarded_changes`. Reported by @RoyPorter (orcaslicer-mcp#10).

### Known issues
- `compare_settings` and `compare_slices` snapshot with `get_config` and restore with `set_config`, so for a per-filament key on a multi-filament setup the restore writes back the merged list. That never actually restored the original: it corrupted the filament preset the same way a manual write did. On OrcaSlicer MCP v2.4.2-mcp.12 and later the restore now fails loudly with `per_filament_length_mismatch` instead of corrupting silently; re-select the filament preset to recover. Making the snapshot/restore path per-filament aware is still to do.

## [0.1.14] - 2026-10-02

### Security
- Config writes that would change a key able to run code or drive the printer are refused with `blocked_by_local_policy` before they reach OrcaSlicer. They are `post_process`, every `*_gcode` template, `printer_model`, `printer_technology`, `filename_format`, and the printer connection settings (`print_host`, `print_host_webui`, `printhost_*`, `host_type`, `bbl_use_printhost`, `printer_agent`, `flashforge_serial_number`). This covers `set_config`, `apply_and_slice`, `edit_preset`, `compare_settings`, `compare_slices` and `set_object_config`. The fork's `PUT /config` accepts any preset key and `post_process` runs through the shell after export, so an assistant steered by injected text could otherwise save a command into a user preset. Thanks to @ferpa for the original change.
- Writing back an unchanged value passes, compared the way the fork serializes it (`true` is `1`). The host address and credentials are always refused, because OrcaSlicer never reports their current value.
- `edit_preset` checks against the named preset before selecting it, so a refusal no longer discards unsaved overrides. The `compare_*` snapshot restores skip the check, since they write back values just read from OrcaSlicer, so a restore never waits on an extra read.
- `ORCA_MCP_ALLOW_KEYS` opts specific keys back in. Wildcards such as `*_gcode` work, and the Claude Desktop extension exposes it as a setting. Names that match no protected key are logged at startup.
- `get_preset_config` hides `printhost_apikey`, `printhost_user` and `printhost_password`, and removes any `user:password@` from `print_host` and `print_host_webui`. The fork returns preset config unfiltered, unlike `GET /config`. Writes carrying the `<redacted>` placeholder are refused, so a round-tripped preset never overwrites a real credential.
- OrcaSlicer MCP v2.4.2-mcp.10 and later enforce the same rule inside the slicer, through Preferences → Remote API → Allow script, G-code and connection edits (off by default). When the slicer refuses a key, the tool reply carries a `hint` that says where the switch is.

### Documentation
- README: Windows fallback for `uvx` failing on `pywin32` with a sharing violation (pip venv, which retries). The same testing found the upstream 2.4.x "Profile syncing change" dialog and the fork's startup `remove_all` crash on a locked AppData datadir.
