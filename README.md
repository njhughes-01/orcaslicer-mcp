# Elegoo Centauri Carbon 2 MCP for OrcaSlicer

This is Nathan Hughes’s community-maintained fork of [OrcaSlicer MCP by Max Ellis and its contributors](https://github.com/MaxEllis/orcaslicer-mcp). It retains the upstream OrcaSlicer tools and adds direct local control and camera snapshots for the Elegoo Centauri Carbon 2. It is independent of upstream, Elegoo, and OrcaSlicer; none endorses this fork.

[![License](https://img.shields.io/badge/license-AGPL--3.0-blue)](LICENSE)

Let Claude work alongside you in a real, running OrcaSlicer. It loads models, arranges the plate, tunes settings, slices, and reads the result back as numbers you can question: which feature ate the print time, what a setting actually does, whether a profile breaks your printer's physics. Every change lands in the GUI while you watch, so the slicer stays yours and you get better at it as you go.

This package is an [MCP](https://modelcontextprotocol.io) server: it bundles no model. It talks to OrcaSlicer, at an address you configure (localhost by default), and, when you use the printer tools, talks to your 3D printer: those tools only read it, and the direct Elegoo Centauri Carbon 2 tools can also control that one printer once you configure its address. No other printer is ever sent a command or uploaded to. The model comes from your MCP client. If that client uses a hosted one, your conversation goes there as any chat does; your models, profiles, and gcode stay on the machine running the slicer. Point the client at a local model and nothing goes to a hosted service.

## What it can do

### Knowing what the settings mean

An offline settings reference ships with the package, carrying the authoritative label, tooltip, type, range, enum, and default for each key, so `describe_setting`, `search_settings`, and `compare_settings` answer from OrcaSlicer's own source instead of guessing. `consult` composes curated slicing knowledge and your saved notes by topic, symptom, or goal.

`check_profile_physics` is a deterministic gate. It overlays proposed changes on the live config, runs flow, temperature, geometry, and cooling math, then returns `ok`, `warnings`, or `blocked`. Accelerations your printer cannot reach and speeds past the flow ceiling get caught before they reach a print.

### Settings

Read and write any of roughly 800 OrcaSlicer settings on the live config, for the whole plate or scoped narrower: `get_config`, `set_config`, `find_config_keys`, `set_layer_height`, `set_height_range` for a band of layers, and `set_object_config` for one object's overrides.

On a multi-filament setup, per-filament keys are read merged across every loaded slot but written one preset at a time, and selecting a preset discards unsaved overrides in every group. So make filament edits first and print edits second; [docs/order-of-operations.md](docs/order-of-operations.md) explains why and gives the sequence.

### Presets

`list_presets`, `select_preset`, `get_preset_config`, `edit_preset`, `save_preset`, `rename_preset`, `delete_preset`. `select_preset` discards unsaved overrides in every group, not only the one switched; see [docs/order-of-operations.md](docs/order-of-operations.md).

### Slicing, and reading the result back

`slice`, `slice_and_wait`, `apply_and_slice`, `cancel_slice`, `get_slice_status`, `get_slice_warnings`, `get_gcode`.

`get_slice_breakdown` returns per-feature time, filament, and flow. OrcaSlicer shows the same information in the legend beside its preview, sized for a screen; this returns it as numbers an assistant can compare and act on:

```
role                    time      share   filament   mean flow
inner_wall              5m 41s    30.8%     6.43 g    16.0 mm3/s
outer_wall              3m 19s    18.0%     3.20 g    13.6 mm3/s
sparse_infill           3m 07s    17.0%     3.57 g    17.0 mm3/s
internal_solid_infill   2m 01s    11.0%     1.72 g    11.8 mm3/s
bridge                     52s     4.7%     0.26 g     4.4 mm3/s
support_interface          36s     3.2%     0.52 g    12.3 mm3/s
overhang_perimeter         28s     2.5%     0.13 g     3.7 mm3/s
internal_bridge            21s     1.9%     0.45 g    19.9 mm3/s
top_surface                19s     1.7%     0.29 g    12.5 mm3/s
brim                       12s     1.1%     0.21 g    14.7 mm3/s
bottom_surface              7s     0.7%     0.10 g    11.8 mm3/s
                        18m 24s            16.89 g
```

It answers which feature is eating the time without slicing repeatedly to find out. A `prediction_check` rides along and flags any role where the profile's requested speed got throttled at the flow ceiling.

`compare_slices` slices the current plate under several named variants and returns one comparison, so "what does layer height actually cost me?" is a single question rather than four manual slices. It applies each variant over your original config, restores it when done, and hands back a verdict plus a table with every delta already worked out:

```
Recommended: 0.4mm - fastest with no warnings.

variant     time      filament   vs 0.4mm (baseline)
0.3mm       8h 10m    41.0 g      +1h 30m (+22%), -7.0 g (-15%)
0.4mm  *    6h 40m    48.0 g      baseline
0.5mm       5h 20m    53.4 g      -1h 20m (-20%), +5.4 g (+11%)
0.6mm       4h 35m    57.1 g      -2h 05m (-31%), +9.1 g (+19%)  thin-wall warning
```

It only crowns a winner when one variant genuinely beats the rest on time, filament, and warnings; when they trade off, it names the fastest, the lightest, and where the warnings landed, and leaves the choice in front of you. Pass `detail=True` for the per-feature split of each variant.

### Models and the plate

`load_model` (`.stl`, `.obj`, `.3mf`, plus `.step` and `.stp` on fork v2.3.2-mcp.3 and later), `list_objects` with each object's world-space bounding box and an `on_plate` flag, `transform_object`, `duplicate_object`, `delete_object`, `arrange_plate`, `auto_orient`, `check_placement`, `diagnose_plate`, `get_job_status`.

### Several plates

`list_plates`, `add_plate`, `select_plate`, `delete_plate` and `move_object_to_plate` build a multi-plate project the way the toolbar does: one part per plate, each sliced on its own. Slicing, G-code, renders and job status always act on the current plate, so select a plate before you slice it. Each entry of `list_plates` carries the copies that plate holds as `{id, instance}` (the object's id and which copy of it), and that per-plate list is what says what a plate prints: an object's own `plate` in `list_objects` names only where its first instance sits, so a duplicated part or copies spread over two plates are invisible there. Keep `arrange_plate` away from a layout like this: OrcaSlicer's arrange packs every unlocked plate together again. These need fork v2.4.2-mcp.13 or later.

`save_gcode` and `recall_prints` follow the same rule: the outcome row describes the copies of the plate that was sliced, never every object in the project, so a print of one plate recalls that plate's settings rather than another plate's, and a plate holding three copies is never matched to the history of a single copy. Where the slicer cannot say what the sliced plate holds (it lists several plates but keeps that plate's copies to itself, names no current plate, contradicts itself about its own plate list, could not be reached for it, the plate was clicked while the slice and its settings and estimates were being read, or the copies on the plate that stayed current changed during that same window), `save_gcode` still saves the file and still records its settings and printer, but leaves the model name, the fingerprint and the time and filament estimates out and says why in the reply instead of guessing them. A fork with no plate API at all is the one build that says nothing about plates honestly, and it is recognised by its missing route, not by a read that failed: those keep recording what they always recorded.

**CANVAS slots.** With an Elegoo Centauri Carbon 2 and a CANVAS unit, `get_printer_slots` reads the trays (label, status, material, colour), `get_filament_slot_mapping` shows which tray each filament of the current plate would use, and `set_filament_slot_mapping` changes that choice. Only the mapping can be changed. Nothing is sent: OrcaSlicer's Send dialog opens pre-filled and you still click Send. For any other printer, or when the printer cannot be reached, the reply is `supported: false` with a `reason` and a message. These need fork v2.4.2-mcp.14 or later.

### Plate renders

`render_plate` hands back a PNG, so the assistant can look instead of inferring from coordinates. A rotation reads instantly as a picture and barely at all as three Euler angles. Seven camera angles cover `iso`, `top`, `front`, `left`, `right`, `rear`, and `bottom`. Use `frame="plate"` to stand back for the whole bed, or `frame="object"` to lean in on the part. Requires fork v2.3.2-mcp.4 or later.

`describe_plate` answers the same questions as numbers and one sentence per object, computed from the sliced G-code: how the part stands (flat, tilted, or on an edge or corner, from first-layer contact against its widest layer), the first-layer footprint as islands, where overhang extrusions concentrate by height band, where support stands and where it touches the part, and which side the seams sit on, checked against `seam_position`. It exists because an assistant reads a sentence more reliably than a picture. Copies of an object are aggregated; the islands still show each copy's contact patch. On a plate of three tilted bracket copies it reads: "bracket.stl (3 copies) stands on an edge or corner: first-layer contact is 5% of its widest layer, in 3 islands of about 50 mm2 each. Overhang extrusions concentrate at Z 0 to 10 mm. Support is present from Z 0.4 to 56.8 mm, standing in 3 places and touching the part in 7 zones. Seams align on the +Y side (91%), matching seam_position=back."

### Live state and memory

`get_status` and `watch_events` report what the slicer is doing now. `remember` persists machine, user, and project facts for later sessions, as plain local files in `~/.orcaslicer-mcp/notes/`, relocatable with `ORCA_MCP_NOTES_DIR`.

### Printer feedback

`get_printer_status` reports what the printer is doing now: idle, heating, printing, paused, finished, or stopped by a fault, with nozzle and bed temperatures, the job's progress and time left, and any problems the printer reports in its own words. Common Klipper messages come with a short plain-English hint. `wait_for_printer` waits until the printer has heated, started extruding, or finished the first layer, or until the job ends (completed, cancelled or failed). OctoPrint reports no extrusion, so there waiting for `printing` means waiting until the job is running with the heaters at temperature. It returns early if the printer reports a fault, or if the job ends before the point it waits for, as when you cancel a print while it heats. It rides out brief network drops: after three failed checks in a row it stops and reports "Lost contact with the printer" along with the last status it saw. `list_print_history` lists recent jobs with how each one ended, how long it took against the slicer's estimate, and, for failed ones, the printer's reason while its console still holds it. `check_printer_match` compares the active profile with the printer's own settings: nozzle size, bed size, speed and acceleration limits, maximum temperatures, and firmware retraction. A check without enough data comes back as unknown, and when nothing could be checked the answer says so instead of reporting a match. Asking for more acceleration than Klipper's `max_accel` earns a warning because current Klipper accepts the higher value when the G-code sets it (`M204` or `SET_VELOCITY_LIMIT`), so the printer accelerates harder than its configured limit. A speed above `max_velocity` is slowed down unless the G-code raises the limit.

The server finds the printer through OrcaSlicer. It reads the address from the active printer profile's connection settings, so there is nothing more to set up once the printer is connected in OrcaSlicer. Klipper printers (Moonraker) get all four tools; OctoPrint gets status and waiting, except for the first-layer wait. Set `ORCA_PRINTER_URL` when that address doesn't work from the machine running this server, `ORCA_PRINTER_API_KEY` when the printer needs a key, and `ORCA_PRINTER_ID` to name the printer in the outcome store. Without it the name is the host name of `ORCA_PRINTER_URL` when that is set, otherwise the printer profile's name, otherwise `unknown`. `ORCA_PRINTER_URL` may carry a user name and password, as in `http://user:password@192.0.2.10`; percent-encode special characters in them, for example `@` as `%40`. A user name and password stored in OrcaSlicer's own printer address are not read, so use `ORCA_PRINTER_URL` or `ORCA_PRINTER_API_KEY` instead. These tools only read from the printer. They never send G-code, change a temperature, or start or stop a job.

### Learning from real prints

`save_gcode` saves the last successful slice's G-code and records the model name, a fingerprint of the copies that plate prints (each object's name and size, once per copy), the full settings snapshot, and OrcaSlicer's time and filament estimates that produced it. On a project with several plates that name and fingerprint cover the copies the sliced plate lists for itself, because the G-code is only ever that plate's; the reply carries the plate's 0-based index, how many copies the row covers, and says how the objects were chosen. The G-code goes into a `gcode` folder under `PRINT_OUTCOMES_DIR` when that is set; otherwise under the shared print-outcomes folder (`~/projects/_shared/print-outcomes/`) if it already exists on this machine, and under `~/.orcaslicer-mcp/` (the same folder `remember` uses) if it does not. `recall_prints` reads the outcome store before you slice, so the assistant can say how past prints of this model actually went: success, cancelled, or the verdict you gave it, the printer's reason when one failed, and the settings used. It looks with the same copies `save_gcode` recorded, and for rows written before copies were counted also with the older form they carry, so nobody loses their history — and because that older form names each part once and so cannot tell one copy of it from three, a match found through it comes with a `legacy_fingerprint_note` saying the copy count is not established. When nothing on record prints the copies this plate prints now, `copy_count_note` says so, and the tool does not reach for the plate's own part name to answer with somebody else's print: a search by name runs only on a `model_name` you pass. When the slicer cannot say what the current plate holds it will not attempt a fingerprint match at all, saying so in `attribution_note`.

`save_gcode` records every slice in a local outcome store, `~/.orcaslicer-mcp/outcomes/` unless `PRINT_OUTCOMES_DIR` says otherwise (an existing `~/projects/_shared/print-outcomes/` folder is used as it is). `list_print_history` copies finished jobs from a Klipper printer's own history into the same store and matches them to those slices by filename, so `recall_prints` learns from real results with no other software. In those rows `duration_s` is Moonraker's whole job time, which includes heating up and any pauses, so beside the estimates it overstates an overrun; `list_print_history` compares the print time, which leaves both out, with the estimate. `filament_g` is the G-code file's own estimate, because printers report filament in millimetres, not grams. The [klipper-mcp](https://github.com/MaxEllis/klipper-mcp) companion still works alongside: its recorder writes each result as the print finishes, and its `start_print` tool uploads the file `save_gcode` saved. A finished print's row you delete from the store by hand comes back, without its saved slice settings, while the job is still in Moonraker's recent history, because `list_print_history` and klipper-mcp's recorder copy recent jobs into the store again; to drop it for good, delete the job from Moonraker's history too. Neither project contacts you on its own; the assistant sees new results when it next calls `list_print_history` or `recall_prints`.

### Direct printing on an Elegoo Centauri Carbon 2

The Centauri Carbon 2 speaks its own protocol (MQTT over LAN with a brief UDP discovery), not Klipper or OctoPrint, so the printer tools above do not apply to it. Sixteen `cc2_*` tools talk to it directly, and they are declared the way every other tool on this server is: **there is no read switch, no write switch and nothing to enable to make them appear.** Configuring the printer is the whole setup. Set `ORCA_CC2_URL` to the printer's host or IP (for example `http://192.0.2.24`) and keep the printer's six-digit access code in a file readable only by your user (`chmod 600`), named by `ORCA_CC2_ACCESS_CODE_FILE`. You may instead set `ORCA_CC2_ACCESS_CODE` directly; configure only one of the two code sources. Until an address is set, every one of them answers `not_configured` with `printer_contacted: false`, and that refusal happens in the server's own process, before any name is looked up and before any socket is opened, so an unconfigured server never touches your network. The code goes only into the printer's own authorization header and the MQTT login — never into a tool result, log, receipt or exception.

- `cc2_status` reads the machine and the filament system: state, the current job, temperatures, and the canvas with each tray's presence, material and temperature limits. It also reports the overhead light and the print speed mode when the printer states them (`led.status` and `gcode_move_inf.speed_mode`), and leaves both null when it does not — an absent reading is never turned into "off" or into the protocol's default mode. Every field comes from the printer's own verified answers; anything it doesn't answer comes back null or missing rather than a guess, and a printer whose answers don't parse is reported as an error instead of status. A machine paused on a filament-out sensor is reported as paused and out, never as running normally.
- `cc2_list_files` returns a bounded page of the G-code inventory — names, sizes, layers, times, filament. The printer is always asked to account for every file it holds, so a listing it cannot prove complete comes back as an error naming the numbers, never as a partial list. What that reply *shows* is a separate fact and the reply says which is which: `offset` and `limit` (both optional — the page starts at 0 and holds 200 files, the most one reply can carry; a bigger limit refuses with that cap named rather than arriving short), and when files were left out the reply owns up to it — `has_more: true`, `next_offset` to ask for the rest, a note naming how many were withheld, and `complete: false`. `complete` is true only of a reply that holds the whole listing itself, and `inventory_complete` is where the printer-side certification lives, so a page never passes for a complete answer and no truncation is ever silent. **`has_more` is the paging stop, never `complete`:** keep calling with the `next_offset` you are given until a reply answers `has_more: false`, because `complete` is the claim of the single reply that held the whole listing and is therefore false on every page of a paged shelf, the last one included. Following `next_offset` while `has_more` is true retrieves every name exactly once; each page re-reads and re-certifies the listing, because a stale listing that swore a file was absent is worse than one extra read.
- `cc2_printer_info` asks the printer what it is (method 1001, which the protocol spells with no parameters at all): its model, the name its touchscreen carries, its serial, its firmware versions, its hardware and protocol versions, its build volume and resolution, its network type, its remaining memory, and whether a camera or a USB drive is attached. It is where a firmware version comes from, because nothing else here reads one. Nothing fills a gap in: every field the printer did not answer is null *and* named again in `not_reported`, since "it said nothing" and "it has no camera" are different facts — this firmware is measured answering two of its three version strings empty, and an empty string is not a version. The serial the printer names is compared with the serial this session connected and pinned, and a disagreement is said plainly rather than believed past. Its `ip` and `mac` are deliberately not returned: the address is the one you configured, and a MAC is a permanent hardware identifier with no task to perform here.
- `cc2_file_detail` reads one file on the printer (method 1046): its size, its total layers, the slicer's estimated print seconds and filament grams, when it was created, how many times it has printed and when last, and the colours it was sliced with per tool (a tool index, never a CANVAS tray — the two are easy to confuse and the protocol says so twice). It uses the same words `cc2_list_files` uses for the same facts, and it uses the printer's file names exactly as printed, never case-folded or trimmed. Three honesty cases are worth knowing before a model reads one: if the printer answers about a different file than the one asked for, the reply says so with both names; the layer count reaches this firmware under more than one field name in the wild, so the reply carries the name that actually answered and, if two names disagree, both numbers and a warning instead of an average; and the printer's refusals stay its own — a nonzero `error_code` keeps its number, because nobody has established what this firmware's per-file codes mean, so none is renamed "file not found" and no request is sent a second time to find out. What the protocol cannot do is worth stating: stock firmware offers no way to read a file's contents back, so this is metadata and never a download.
- `cc2_file_thumbnail` returns the preview image the printer holds for one of its files (method 1045) as an image plus one short line of text naming the file, its size and its type. Three things about it are unusual. The picture is the printer's own embedded preview, so a file sliced without one simply has none, and that comes back as a plain sentence saying so rather than a blank image — the file itself is fine and `cc2_file_detail` still reports it. The image type is read from the bytes' own signature (png, jpeg, gif, webp) rather than assumed, because the printer's own web interface stamps every thumbnail `image/png` whatever it is holding; bytes of a type this server has not established are refused with their first bytes named rather than sent on under a guessed type. And because the image travels inline inside one tool reply, a decoded image over 2 MiB is refused with its size named and **never truncated to fit**: a half an image is a corrupt image, and that limit is about the conversation, not the printer. One quirk of these two file methods is real and pinned by tests — 1045 wants the parameter spelled `file_name` and 1046 wants `filename`, so they are not interchangeable, whatever a tidy refactor would prefer.
- `cc2_print_history` reads the print history the printer keeps for itself (method 1036, **asked with no parameters at all**, once): each print's name, the printer's own status number next to the word the printer's own app paints for that number, when it began and ended, how long it ran, and whether a time-lapse exists. It returned 50 entries on Nathan’s CC2 in a live check; its interpretation and behavior on other firmware remain unverified: the fields it reads are exactly the fields Elegoo's own LAN web client reads out of `history_task_list` when it sends 1036 with nothing else, its duration is the same subtraction that client performs, and a reply shaped any differently is refused rather than fitted to that shape — so a refusal out of this tool is evidence about your firmware, not a broken printer. Two traps are pinned by tests. The community protocol table lists 1036 with `{"page": 1, "page_size": 10}`, and that is Elegoo's *cloud* history call (paginated by `pageNumber`/`pageSize`, answered in camelCase `taskList`/`totalTasks`): this request sends no paging of any kind, and a cloud-shaped reply refuses with a reason of its own instead of being read as a LAN answer. And because the request carries no page size, the **printer** decides how long the answer is — so the reply caps itself at 100 entries and then says so out loud (`truncated_in_reply`, both counts, a warning) and never as the whole list, with no next page to ask for, since 1038 *removes* history entries and this server does not send it; the cap sits under the sanitiser's own list cap so a truncation is always this tool's own sentence rather than a silently dropped row. `complete` is true only when the printer's own `total` meets the entries it actually sent: a count above them, below them, unreadable, or absent each get their own sentence, and an empty list with no count says the one thing that can be said, which is that an empty history cannot be told apart from a firmware that keeps history somewhere else. The status word is labelled as an app's vocabulary rather than a protocol's (that table gives two of its numbers the same word), so the raw number is always carried too, and no unit or meaning is claimed for the time-lapse numbers. Entries stay in the printer's own order — nothing here sorts, filters or de-duplicates what it sent. Over-long text is withheld with its length named rather than cut in half, and a time-lapse link carrying a login (`user:pass@`) is withheld entirely with only its presence reported, because this server repeats no credentials. **Method 1037 (one print's detail) and 1038 (deleting history) are not offered:** 1037 has no published request or response anywhere in the sources — its name appears in Elegoo's own web bundle only in the enum that defines it, never called — so there is nothing reliable to read, and no `uuid` is taken out of a live status frame and sent somewhere as a task handle.
- `cc2_camera_snapshot` takes **one picture** from the printer's own camera and returns it as an image with its metadata beside it as text — a summary line naming its size, its type and where it came from, carrying the single-viewer warning with it, and the whole sanitised metadata the adapter built as JSON: exactly one bounded HTTP GET of the stream at the configured printer's address (its camera port and stream query), and the first complete JPEG frame found in it. It is the one CC2 tool that reaches the printer without its protocol — no discovery, no MQTT session, none of the printer's client slots spent, **no command sent and no printer method asked at all**. The printer's own camera-address method is still not exposed and still never sent, because nobody has captured a reply from it on this firmware or settled whether it toggles the stream, and a picture from the stream is not evidence about it in either direction. So the address is **composed here from the configured host** (never hardcoded, never advertised by the printer, and named in the reply as composed) and then held to the same policy as MQTT: the printer's literal private LAN address, with no resolver left standing between that decision and the socket, no proxy honoured from the environment, and no redirect followed — a 3xx is a refusal naming its status, not a hop somewhere this server's LAN policy never judged. Because a stream by definition never ends, the fetch is bounded hard and never quietly: one request, never a second one after a timeout or a failure; a 10 second window measured from the moment the request starts, enforced tightly enough that a stream trickling one byte a second cannot outrun it; at most 8 MiB consumed while hunting for a frame, counted **before** a chunk is appended or accepted so a frame that only becomes reachable past that ceiling is refused with the ceiling named rather than kept; and the kept frame capped at 2 MiB, the same ceiling `cc2_file_thumbnail` holds, refused with its size named and **never truncated to fit**. What arrives first on a live stream is usually the tail of a frame the camera began before this server connected, and that tail is dropped rather than reported, so a snapshot is always a whole frame or an honest refusal — and the hunt walks the frame's own segments instead of grabbing at the first end-of-image bytes it sees, because an EXIF block can carry a nested thumbnail that ends with a marker of its own, and cutting there would hand over the head of a real frame as if it were a picture — and it keeps walking past the **first** scan, because a multi-scan (progressive) frame redefines its tables between its scans and those payloads can hold end-of-image bytes of their own, so the walk honours each segment's declared length and stops only at the frame's own end marker, refusing a candidate whose marker cannot legally follow a scan rather than returning a frame with a hole in it. Two things it is not: the protocol manual describes this stream as usually allowing a **single viewer**, so opening it may be refused or may displace whoever was already watching, which the reply says out loud instead of finding out by asking twice; and the camera may not show every part of the print bed. On credentials it is stricter than it needs to be: the address cannot carry a login because this server builds it, only one sanitised `Content-Type` word is kept from the reply's headers, and no header value and no byte from before the frame ever reaches a tool reply.
- `cc2_upload_gcode` sends one local sliced `.gcode` file to the printer in 1 MiB chunks, requires an HTTP 200 response with an explicit zero error code for each chunk, then verifies the uploaded filename and size against the printer’s complete listing. A destination name that already exists on the printer is refused before any byte leaves: this workflow never overwrites, so choose a fresh name. It never deletes or renames anything on the printer or on disk, and after a success it records a private receipt on your machine (under `ORCA_CC2_RECEIPTS_DIR` if set) holding the printer, filename, byte size, the file's content hash and what the printer reported — never the access code or a password. A failed or interrupted upload is never automatically retried, and may leave a partial file under that name, because no CC2 delete has been proven to work on this printer, and this server never deletes anything for you. The file's own commands are held to a list, and a command off that list refuses the upload: the parser accepts the linear moves `G0` and `G1`, the arcs `G2` and `G3`, the `G4` dwell, homing, unit and coordinate modes, the four heat setpoints and waits, the part fan as `M106` and as its off-switch `M107`, the acceleration, progress and stepper commands, the Elegoo flush command, one tool select, and the four Klipper words the slicer emits (`BED_MESH_CALIBRATE`, `SET_PRESSURE_ADVANCE`, `SET_PRINT_STATS_INFO`, `SET_VELOCITY_LIMIT`) — because each one is written down with the reason it cannot change a heater target or push filament. None of those four real slices ever wrote `G0`, `G3`, `G4` or `M107`, and they are on the list for what they mean, not for what a slicer was seen doing: `G0`/`G3` were already read as moves here, with an `E` on either gated by the same `M109` rule as `G1`, and the two whose inertness is a claim about their *parameters* — a dwell is a duration, a fan-off is a fan — are accepted only with the parameter letters their dialects document, so `G4 P100E6`, `G4 U255` and `M107 R200` refuse the file. Command and parameter letters are matched whatever their case, as this parser already matched command words, tool selects, compact codes like `m109s240` and move letters like `g1 x1e6`: `M104 s140` sets the setpoint `M104 S140` sets and `G180 s7` selects the macro `G180 S7` selects — and only the letter folds, never the count, so `M104 S140 s200` is still two setpoints and still refuses. Anything else is refused with the offending line named and nothing sent, including a word-form macro this adapter cannot read (a macro's body can heat or extrude invisibly) and the firmware retract and clean-up commands `G10`/`G11`/`G12`. `G180` is worth naming separately because it is not one command: in the Centauri Carbon 2 firmware it is the printer's own macro dispatcher, so `G180 S7`, `S8` and `S9` run macro bodies held in the printer's `[g180]` config section — the CC2 profile uses them for its bed-mesh profile loads and for its end-of-print filament unload. It is therefore allowed by number and never by name: those three numbers are accepted because each one's body was read against Elegoo's published CC2 firmware and configuration, and any other number refuses the file, because an unread `[g180]` macro heats, waits, purges, cuts or withdraws filament. That evidence is the published source, not your machine's running firmware — a CC2 cannot report its `[g180]` section back, so a printer whose config was edited elsewhere can differ. And because `S9`'s unload happens or not depending on live printer state (whether the filament system is linked, whether there is filament in the head, how hot the nozzle already is) and can wait at its own temperature, the guard stops trusting its own temperature history at that line and refuses any extrusion after it, which is how the slicer's own end block is written anyway. Every extrusion in a file must follow an `M109` that waited at the temperature it runs at (a non-extruding preheat is fine), and a file whose config promises a temperature its commands never set, or that selects more than one tool, is refused the same way.
- `cc2_start_print` starts one already-uploaded file and never uploads anything itself. Because the CC2 has no tool-slot array, you pass the mapping yourself — the file's tool number to the canvas tray to load it from, exactly one tool for now — and the print refuses if the tray isn't present and printable or if the mapping doesn't name a tray on the printer. `bed_clear=true` is the physical bed-clear assertion; `leveling` defaults to off, sent explicitly, because the printer remembers the last value. A start refused because the printer answered *busy* is reported as refused-busy without any retry, and a start the printer never answered is reported as unknown — the command may have started, so it is never sent again. After an accepted start, one separate look at the printer says whether it is observed printing that exact file; acceptance and observation are kept apart either way.
- `cc2_pause_print`, `cc2_resume_print` and `cc2_stop_print` are the job controls, and each is two-phase the way the maintainer's Klipper MCP companion is: without `confirm=true` a call reads the printer once, returns a preview (the current job and the exact command a confirmed call would send) and sends nothing at all; only an exact `confirm=true` sends the one command — the confirmation is enforced by the server, because a client can run with permission prompts off. What `confirm=true` carries is the user's authorization for that action: a yes they already gave for this print or this session is that authorization, so the tool never has to ask them again, and the preview is there for when nothing authorizes it yet. A confirmed call sends its one MQTT command (pause 1021, stop 1022, resume 1023 — the protocol spells all three with no parameters) exactly once, waited for the official Elegoo UI's own window: 60 s for pause and stop, 120 s for resume. Know the resume fact before you call: the printer is measured answering the resume command only once the resume has actually completed — reheat, homing and return-to-position first, 122 s to its `error_code` 0 answer on firmware 02.01.00.00, longer than the UI's own 120 s window — so a resume call can take the full two minutes, and a window that expires is reported as the expected outcome of a real resume that it is: never a refusal, never a failure, and never a reason to resend. Every result keeps three facts apart — accepted (the printer answered `error_code` 0, it did not refuse), refused (an explicit code kept; 1010 is the documented "no active print") and ambiguous (no answer, an unreadable one, or a dropped session) — and after an accepted or unanswered command one separate read-only look reports what the printer says it is doing, never overwriting acceptance: an accepted resume is never required to already report running. Stop is the irreversible one: the documented machine state ends a stopped job at STOPPED, while pause and resume are the reversible pair. Nothing here pre-checks whether the command makes sense right now — the human reads the preview, and the printer itself refuses (1010) when there is nothing to do.
- `cc2_set_light` and `cc2_set_print_speed` are the two peripheral controls, and they run the same two phases for the same reason. `cc2_set_light` is the printer's overhead light, on or off: the CC2's own doc table spells the parameter `brightness` while the doc's own findings and the printer's own LAN web client spell it `power` (1 on, 0 off), so the command carries both spellings paired so they can never contradict each other (`power` 1 with `brightness` 255, `power` 0 with `brightness` 0), which is what the Home Assistant integration does for exactly that reason; the light is binary because no source shows it dimming. `cc2_set_print_speed` takes the printer's own **discrete mode**, never a percentage: 0 Silent (50%), 1 Balanced (100%, the printer's default), 2 Sport (150%), 3 Ludicrous (200%). Any other number — including 45 or 150, which are what a percentage-shaped guess produces — is refused with those four named and nothing sent. One command each, sent once, waited for 10 s: that is the longer of the two first-party windows, since the official LAN client waits 5 s for these two methods and the integration waits 10 s for every command it sends. Accepted, refused and ambiguous are kept apart exactly as they are for the job controls, a lost answer is never a refusal and never earns a resend, and after an accepted or unanswered command one read-only look reports what the printer now says about its own light and mode. That look is taken straight after the command, and nothing measured says how soon this printer's status reflects one, so it can be showing a status that has not caught up rather than a change that failed — `cc2_status` asks it again. If the look contradicts a command the printer accepted, a note says so plainly and still sends nothing a second time. The one peripheral the sources do **not** settle is deliberately absent: the fan (1030 — the doc table, the integration and the official UI disagree about its scale, and it goes in only once that is verified against the printer).
- `cc2_set_temperature` sets one heater's target (method 1028, `{"extruder": n}` or `{"heater_bed": n}` — the two frames Elegoo's own LAN control sends, one heater per command, so the heater you did not name keeps whatever it was at), and it runs the same two phases: no `confirm=true`, no command. What makes a heater command different from a lamp is the ceiling, and this one is not invented: **0-350 for the nozzle and 0-110 for the heated bed are the input bounds of Elegoo's own official LAN control for this printer** (its web client, release 20260625, which clamps a typed number into them before it sends), and every reply carries the bound with that source beside it. They are the official control's bounds and never presented as what the hot end or the bed is rated to. Nothing in the sources offers a usable alternative: the printer's own firmware refuses a setpoint outside its configured window by itself (`max_temp` 600 extruder and 125 bed in Elegoo's published CC2 config — a sensor envelope, not a target), the same Elegoo SDK records 300 for that extruder in a capability row whose own field order contradicts it, and the official Elegoo slicer profile bundle for this machine carries **no temperature-ceiling key at all**, which is why a profile's nozzle or bed number is a print setting and is never used here as a machine limit for other filaments or nozzles. So there is no parameter that raises a ceiling — a caller-supplied ceiling is the guess this refuses — and asking for less is always open. A nozzle number above the 300 the other source names is still sent, because the machine's own control reaches that high, with the disagreement said out loud instead of resolved on a hunch. `heater` is `'extruder'` (or `'nozzle'`) or `'heater_bed'` (or `'bed'`), and anything else refuses before a session opens — including `'chamber'`, because that row is a reading, not a control: the official control shows it not editable and the published firmware config gives the box a sensor with no heater behind it. `0` is a legal target and says what it means: the heater is off, which is what this printer's own end-of-print G-code sends. One command, sent once and never resent, waited for 10 s (the longer of the LAN client's 5 s default for this method and the integration's 10 s for every command); accepted, refused and ambiguous are kept apart exactly as they are for the other controls; and after an accepted or unanswered command one read-only look reports both the target and the actual temperature the printer states, kept apart from acceptance — a target still climbing is never read as a failure, while a target stated as something other than the number just accepted is said out loud without earning a second command.
- `cc2_set_auto_refill` flips the CANVAS auto-refill switch (method 2004): one boolean, and **one CC2 changed and restored the setting; automatic refill during a print remains unverified**, which is why every one of its replies carries `verified_on_this_printer: false` beside the sentence saying why. That label is the point of the tool: the shape it sends is first-party and narrow, and nothing more is claimed for it. Elegoo's own LAN web client, the bundle the printer serves itself, defines `SetAutoFillFilament = 2004` and `GetCanvasInfo = 2005` in its own enum, builds the command as `{method: 2004, params: {auto_refill: <the toggle's boolean>}}`, treats a nonzero `error_code` as "Failed to set auto refill.", and paints that same toggle from `canvas_info.auto_refill` of the 2005 reply — so the field the printer's own client sends and the field the printer answers are one name, and that field is all this tool ever sends. **The older integration protocol manual spells this parameter `enable`, and that spelling is never sent here, in any combination** — not instead of `auto_refill` and not paired with it the way the light sends both of its spellings. That manual is the only source for `enable`; its own 2005 sample answers `auto_refill`, the integration that ships it defines the 2004 constant and never sends it, and the same manual makes the same class of mistake on the delete command (its table says `filename` where Elegoo's client sends `file_path`), which is the general reason a table row of that manual is not treated as proof about this firmware. Because 2004 sits beside 2003 (which writes a tray's filament info) and the 2005 reply carries `active_canvas_id` and `active_tray_id` next to the flag, sending one field is a safety property: a call here cannot move which tray the printer prints from, rename a spool or change a slot map, and it sends no other method. Two phases like the rest: without `confirm=true` a call sends only the read-only CANVAS read (2005) and previews what the printer says now and the exact one-field command a confirmed call would send. One deliberate difference: unlike the light and the speed mode, a CANVAS read that answers nothing **does not** block the preview or the change, because a printer with no CANVAS attached is a legal state for a switch the printer stores for itself — and what matters is that this is never turned into a `false`: an absent field, a refused read and an unreadable value each stay unknown, with whatever did arrive kept beside them (0 and 1 read as the numbers they are, since the integration's own CANVAS model records another Elegoo machine answering int 1 where its client expects a boolean). Accepted / refused / ambiguous are kept apart exactly as the other controls keep them, the command goes once and is never resent, the wait is 10 s (Elegoo's client passes no override for this method so its 5 s default applies, and the integration waits 10 s for every command, so the longer is taken), and after an accepted or unanswered command one read-only 2005 reports the flag as a fact of its own, with the disagreement said out loud when it contradicts what the printer just accepted. What has **not** been observed is what the flag does when a tray runs dry, and a refusal out of this tool is worth recording for that reason: it is evidence about your firmware, not a broken printer. `cc2_status` already carries the flag, so the read side needs no new tool. **The real-printer test stays open**, and it is the only thing that will move the label: an idle printer, a CANVAS with a spare tray, Nathan's yes for the switch itself, a print run deliberately to one empty tray, and the setting restored afterwards.

One session, not one per call. The CC2's own MQTT broker takes about four clients, and the printer reaps a client that has gone on its own clock, so when every tool call registered its own client, used it for one read and closed it, four ordinary calls in a row were enough to be refused with `too_many_clients` by a printer that was idle and healthy. So **fourteen of the sixteen tools share one registered session per server process**: the first call registers it, the rest use it, and its heartbeat is what keeps the printer from timing us out. Two calls at the same moment never register twice — only the *opening* is serialised, while requests on an open session run side by side because every answer is matched to the request id this server stamped on it. A session that the transport reports dead, or that your configuration left behind (change the address or the access code and the next call opens a fresh one), is closed and the next call opens a new session; that never repeats a command, because the pool sends nothing itself and an unanswered command stays exactly as unresolved as the reply that reported it said. With nothing holding it, the session is closed after two minutes so a printer you have finished with gets its slot back, and closing the server closes it too. What is **not** shared is anything across processes: two MCP server processes — say two agents, or an agent plus your own script — are two clients each holding a slot, and the printer's roster is still the limit. The sixteenth tool is the one exception, and a deliberate one: `cc2_camera_snapshot` is a picture taken over HTTP, so it registers no client, spends none of the printer's four slots, and still works when the roster is full — what it shares with the transport is the configured address and the address pinning, never the session.

**CC2 features not exposed:** File deletion, the fan's speed, manual home and movement, filament load and unload, and **camera control** are not available as MCP tools. Their request formats or behavior have not been sufficiently verified on this printer. The camera is exposed as a picture and nothing more: `cc2_camera_snapshot` fetches the stream, while the printer's own camera-address method — which the community sources describe as a toggle, with no reply ever captured from this firmware to check that against — is neither sent by this server nor offered as a tool by it. In practice: this MCP can look at the camera, and cannot switch anything about it. Stock CC2 sources do not establish a supported G-code download endpoint. Firmware update and factory reset are not implemented. These omissions should not be read as evidence that the printer lacks the underlying capability.

A slicer bed warning for the exact file can be carried through `cc2_start_print(bed_warning=...)` so the start result keeps it, but the server cannot know which file a string you type belongs to — the CC2 stores no sidecar and cannot read uploaded content back — so it never attaches slicer warnings on its own and never claims the warning is about the file. Beyond the commands the tools actually send, nothing in this path deletes, calibrates or moves any axis outside a job the printer is running, and the only temperature it changes is the one `cc2_set_temperature` commands, inside the bound its own official control imposes: every control tool is one command each, never resent, and every refusal or lost answer says plainly whether the command could have left, which is the whole difference between "the printer may be printing" and "it is not". The four information reads over the printer's protocol are one request each (1001, 1036, 1045, 1046), asked once, and no command of any kind; `cc2_camera_snapshot` is one HTTP GET of the printer's camera stream, asked once and sending no command either; and the two tools that return an image (`cc2_file_thumbnail` and `cc2_camera_snapshot`) never return a partial one.


## What you need

Stock OrcaSlicer ships without a control API, so a matching build does that half of the job.

1. **The OrcaSlicer MCP build.** OrcaSlicer 2.3.2 with an embedded local API, token-authenticated and bound to localhost until you say otherwise. Get it from the [releases page](https://github.com/MaxEllis/OrcaSlicer/releases). If no binary is up for your platform yet, build the `remote-api` branch from source.
2. **This package (`orcaslicer-mcp`).** The MCP server that connects your AI client to that build.

> **Updating:** take new builds from the [releases page](https://github.com/MaxEllis/OrcaSlicer/releases), never from inside the app. The in-app updater offers *stock* OrcaSlicer, which drops the control API. Builds mcp.2 and later turn that updater off for you. On an older build, click **Skip this Version** if a "new version available" prompt appears.

## Quickstart

This fork's CC2 changes are on the `feat/cc2-direct-print` branch, and **this fork is published nowhere yet**: no PyPI release, no MCP-registry listing, no GitHub release, and that branch is not pushed. So the only working install today is a checkout of this fork with that branch present — `git fetch && git switch feat/cc2-direct-print` in a clone of [njhughes-01/orcaslicer-mcp](https://github.com/njhughes-01/orcaslicer-mcp) once the branch is pushed, or the checkout itself while it is local. Do not run `scripts/cut-release.sh` or the *Publish to MCP Registry* workflow from this fork: the PyPI name `orcaslicer-mcp` and the registry namespace `io.github.MaxEllis/orcaslicer-mcp` belong to upstream, and `uvx orcaslicer-mcp` therefore always installs upstream's build, which has none of the CC2 tools below.

1. Install the [OrcaSlicer MCP build](https://github.com/MaxEllis/OrcaSlicer/releases), complete its setup, and enable Remote API in Preferences. Keep the generated API token private.
2. In the fork checkout, install the dependencies with `uv sync`. Configure your MCP client to run the checkout's absolute `.venv/bin/orcaslicer-mcp` path (on Windows, `.venv\Scripts\orcaslicer-mcp.exe`). The executable name is retained for compatibility.
3. Set `ORCA_API_TOKEN` in your client configuration, and set `ORCA_API_URL` if the slicer is not at `http://127.0.0.1:13130`. To use the direct CC2 tools, configure `ORCA_CC2_URL` and, if needed, the access code as described in the CC2 section above. Keep credentials out of shared project files and version control.
4. Restart the MCP client. Its available tools depend on the client's own access settings. The upstream release packages and `uvx orcaslicer-mcp` install upstream, not this fork.

## Security

- The control API binds **127.0.0.1 only** by default. LAN access is an explicit opt-in in Preferences.
- Every request must carry the API token. OrcaSlicer generates it on first run and can regenerate it at any time.
- The MCP server runs as a local stdio process. Its only connections are to OrcaSlicer and, when you use the printer tools, read-only HTTP GET requests to your printer at the address in OrcaSlicer's active printer profile (or `ORCA_PRINTER_URL`). It sends that printer no commands and uploads nothing to it. No telemetry. The `cc2_*` tools are the exception and the difference is configuration, not a switch: with no `ORCA_CC2_URL` they open no connection at all and answer `not_configured`, and once you configure one they reach that printer, and only that printer, on UDP (one discovery packet), MQTT over TCP and HTTPS, to read state, the file inventory, the printer's own attributes, one file's detail, one file's thumbnail and its own print history, to upload a file, and to send the control commands — start, pause, resume, stop, the overhead light, the print speed mode, one heater's target temperature, and the CANVAS auto-refill switch — **plus one plain-HTTP GET of that printer's own camera stream, once, bounded in time and bytes, with no credential sent, no proxy honoured from the environment and no redirect followed, and the connection handed back on every path** (that fetch is the camera picture, and it sends the printer no command; the printer's own camera-address method is never sent, because whether it toggles the stream is unverified on this firmware). The thumbnail read and the camera snapshot move an image into the conversation as an image; nothing on this server writes either one to disk. Nine of the sixteen change printer state (the upload, the start, the three job controls, the three peripheral controls and the CANVAS switch), so they are the tools to approve as a human decision: all seven control tools additionally refuse to do anything at all until a second call carries `confirm=true`, which the server enforces because a client can run with permission prompts off. The temperature control goes one step further than the others about its own numbers: the ceiling it will accept is the bound of the printer's own official control (350 nozzle, 110 bed), it says so with the source in every reply, and nothing a caller passes can raise it. Tool annotations are hints to a client, never a permission. The printer's access code is sent only in the printer's own authorization header and the MQTT login, and every tool result, error and receipt passes through a sanitizer that redacts it, strips control characters, and bounds strings and sizes.
- The MCP server refuses to change config keys that run code or drive the printer directly. They are `post_process`, every `*_gcode` template, `printer_model`, `printer_technology`, `filename_format`, and the printer connection settings (`print_host`, `printhost_*`, `host_type`, `printer_agent` and the rest of OrcaSlicer's physical-printer keys). The list lives in `src/orcaslicer_mcp/guard.py`. An assistant holding the API token can be steered by text it reads, such as model names, G-code or web pages. Since `post_process` runs shell commands after export, these stay a human decision in the OrcaSlicer GUI.
- Writing a key back to the value it already has is allowed, so restores keep working. The host address and its credentials are the exception. OrcaSlicer never reports their current value, so any write to them is refused. `edit_preset` runs the check before it selects the preset, which means a refused edit leaves your unsaved changes alone.
- To let the MCP write specific keys anyway, list them in `ORCA_MCP_ALLOW_KEYS`, comma separated. Wildcards work, for example `*_gcode`. The Claude Desktop extension exposes it as a setting. At startup the server logs any name that matches no protected key, which is usually a typo.
- This check covers the MCP server's own tools only. An assistant that can also run shell commands could read the token and call OrcaSlicer directly. OrcaSlicer MCP v2.4.2-mcp.10 and later apply the same rule inside the slicer, and it stays on until you tick **Allow script, G-code and connection edits** in Preferences → Remote API. On those builds the assistant needs both: that box ticked and the keys listed in `ORCA_MCP_ALLOW_KEYS`.
- `get_preset_config` hides `printhost_apikey`, `printhost_user` and `printhost_password`. It also hides the `user:password@` part of `print_host` and `print_host_webui`, cutting at the last `@`, so a password that contains `/`, `@`, `?`, `#` or a space is hidden too. A URL with an `@` in its path loses the part before that `@` as well, because it looks the same as a password with a `/` in it. A value carrying the `<redacted>` placeholder is never written back.

## Privacy policy

The server talks to OrcaSlicer's local API at the address you configure, localhost by default, and, when you use the printer tools, to your 3D printer at the address in your OrcaSlicer printer profile (or `ORCA_PRINTER_URL`). It talks to nothing else. It has no backend, so there is no service of ours for anything to reach. Apart from those printer requests, what leaves your machine is whatever your MCP client sends its model: the conversation, plus any settings or file contents you or the assistant put into it. Their terms govern that traffic, and it is the same traffic any other use of that client produces. A local model removes it entirely.

- **Data collection:** none. The server collects nothing about you or your usage.
- **Usage and storage:** models, settings, and gcode stay on the computer running OrcaSlicer. They pass through the server in memory while a request runs, and the server writes to disk only what the data-retention entry below lists. The API token authenticates the server to OrcaSlicer, and your MCP client stores it. The printer key, if you set `ORCA_PRINTER_API_KEY`, authenticates the server to the printer and is stored the same way. Printer status, history, and settings come back to your MCP client as tool results, so they join the conversation like any other tool output. Claude Desktop keeps the settings marked sensitive (the OrcaSlicer API token and the printer key) in the operating system's credential store. A password in `ORCA_PRINTER_URL` is stored as an ordinary setting, so prefer `ORCA_PRINTER_API_KEY` where the printer accepts a key.
- **Third-party sharing:** none by this server, which has no analytics and no backend. Traffic between your client and its model provider sits outside this project and falls under their policies.
- **Data retention:** the only data written to disk is notes you save yourself with `remember`, stored as plain files under `~/.orcaslicer-mcp/notes/`; the G-code that `save_gcode` writes, under `~/projects/_shared/print-outcomes/` when that shared folder already exists, otherwise under `~/.orcaslicer-mcp/`; the outcome store (`outcomes.db`), which holds slice records (the model name, a fingerprint of the objects' names and sizes, and the settings each slice used) and the finished-print results `list_print_history` copies from your printer, in that shared folder when it exists, otherwise in `~/.orcaslicer-mcp/outcomes/`; and `~/.orcaslicer-mcp/printer.json`, which remembers the last printer address that answered (never a password). When you use `cc2_upload_gcode`, a verified upload also records a private receipt per file under `ORCA_CC2_RECEIPTS_DIR` when set, otherwise `~/.local/share/orcaslicer-mcp/cc2-receipts/` (its own directory, never inside a repository; the folder and its files are created mode 700/600) — the printer serial, filename, byte size, the file's SHA-256, and the printer's own reported layers, time and filament, which is what `cc2_start_print` requires to trust a file; never the access code or a password. `PRINT_OUTCOMES_DIR` relocates the G-code and the store. Read or delete any of it whenever you like. Delete it and nothing remains.
- **Fork issues:** report fork-specific problems in [Nathan’s fork](https://github.com/njhughes-01/orcaslicer-mcp/issues).

## Status

The CC2 fork is in development. What has been exercised against a real Centauri Carbon 2 (firmware 02.01.00.00) is the direct path itself: `cc2_status`, `cc2_list_files`, `cc2_upload_gcode`, `cc2_start_print`, `cc2_pause_print`, `cc2_resume_print`, `cc2_stop_print` and one `cc2_camera_snapshot` picture, with the started file sliced at 260 °C nozzle / 80 °C bed PETG. Automatic CANVAS refill during a print, the printer’s own camera-address method, file-list paging beyond what has been read, and peripheral read-back timings remain unverified. Firmware and features not covered by those checks may behave differently, and a refusal out of a CC2 tool is evidence about your firmware, not a broken printer.

What is deliberately **not** offered stays not offered: file deletion, the fan's speed, manual home and movement, and filament load and unload exist in this tree as internal candidates that no client can reach, and camera enable/disable is not exposed; `cc2_camera_snapshot` does provide an image. Upstream’s prebuilt OrcaSlicer MCP builds are available on the [upstream releases page](https://github.com/MaxEllis/OrcaSlicer/releases).
